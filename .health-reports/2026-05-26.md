### [M-037] `actions/investments.ts` has no auth check and no amount validation (NEW, **Medium-High**)
- Severity: **Medium-High** (financial-data integrity, but partially mitigated by Supabase RLS)
- Category: Bug / Data Integrity / Security
- File or Source: `actions/investments.ts:5-46`
- Problem: `createInvestment` and `updateInvestment` write directly to the `investments` table with **zero defensive input validation**. There is no `Number.isFinite(amount)` guard, no non-negative check, no upper-bound cap, no NaN check. A caller invoking the server action directly with `amount: Number.NaN`, `amount: -50_000_000`, or `amount: 1e30` will succeed if Postgres accepts the cast — corrupting the platform's authoritative investment ledger. Worse, the file is **inconsistent with itself**: `actions/founder-updates.ts:43-51` defines a thoughtful `isInvalidMetric` helper that rejects non-finite, negative, and `>1e15` values on KPI inputs, but the **same numeric data** taking the much more authoritative path through `createInvestment` is not subject to any of those guards. RLS may catch unauthenticated callers, but RLS does not validate numeric ranges. Additionally there is no explicit auth check (`getUser()` + early return) — every sibling action that handles privileged data (`actions/team-members.ts`, `actions/profile.ts`, `actions/founder-updates.ts:generateUpdateToken`) does this in defence-in-depth.
- Recommended fix: (1) Mirror the `isInvalidMetric(v, allowNegative=false)` pattern from `actions/founder-updates.ts` into a shared `lib/validation.ts` helper, and call it on `amount` and `valuation_cap` in both create + update. Reject with `{ error: 'Amount out of range' }` before the DB call. (2) Add `const { data: { user } } = await supabase.auth.getUser(); if (!user) return { error: 'Not authenticated' }` at the top of both server actions — matches the pattern in `team-members.ts:16-18`. (3) Same shape for `actions/safes.ts:createSafe/updateSafe/deleteSafe` and `actions/rounds.ts:createRound/updateRound` — they have the identical gap.

### [M-038] `actions/team-members.ts:deleteTeamMember` has no self-deletion guard (NEW, Medium)
- Severity: Medium
- Category: Security / Availability
- File or Source: `actions/team-members.ts:58-75`
- Problem: An admin can call `deleteTeamMember(self.id)` and remove themselves. If they are the only admin on the platform — common for a small foundation team — every subsequent admin-gated action (`createTeamMember`, `updateTeamMember`, the new admin gates added in the uncommitted M-016 work) becomes uncallable. The sibling `updateTeamMember` already explicitly handles the self-modification case by stripping the `role` field (lines 47-50) precisely to prevent admin-loss scenarios; the delete path needs the same instinct. The user-deletion would also orphan task assignments (`task_assignees.assigned_to`) and any `owner_id` reference on companies/pipeline pointing at the deleted admin, unless an FK ON DELETE cascade is configured (worth verifying).
- Recommended fix: After the admin check, before the delete, add:
  ```ts
  if (id === user.id) return { error: 'You cannot delete your own account.' }
  ```
  Optionally add a second guard counting remaining admins and refusing if this would leave zero admins:
  ```ts
  const { count } = await supabase.from('team_members').select('id', { count: 'exact', head: true }).eq('role', 'admin')
  if ((count ?? 0) <= 1) return { error: 'Cannot delete the last admin.' }
  ```

## IMPROVEMENT IDEAS

1. **Stop relying on RLS alone for numeric validation of financial data.** M-037 makes the gap concrete: `actions/founder-updates.ts` does thorough `isInvalidMetric` checks on KPI inputs, but the much more authoritative `actions/investments.ts`, `actions/safes.ts`, `actions/rounds.ts` don't. Extract `isInvalidMetric` from `founder-updates.ts` into `lib/validation.ts`, call it on every numeric field crossing a server-action boundary, and add a brief unit test for the most common shapes (NaN, negative, 1e16, Infinity). RLS is the perimeter against unauthenticated callers; range-validation is the perimeter against authenticated mistakes and bugs. Both are needed.

2. **Audit-driven worktree GC.** The 15+ stale worktrees in `.claude/worktrees/` show up in every Grep, slow every audit, and serve no purpose after their agent session ends. A `~/.claude/hooks/post-session-cleanup.sh` that runs `git worktree prune && find .claude/worktrees -mtime +7 -maxdepth 1 -type d -exec rm -rf {} +` would solve the entire class. Cheap, high-leverage.
