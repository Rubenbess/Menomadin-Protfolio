## FIXED ISSUES

### [F-001] `fmt$$` rendered every negative currency figure unscaled
- File: `lib/calculations.ts:547-556`
- Problem: The scaling thresholds were compared against the **signed** amount, so all negative values fell past the B/M/K branches into the fallback. A -$5,000,000 write-down rendered as `$-5,000,000` instead of `-$5.0M`. `fmt$$` is the platform's primary currency formatter — it renders reserve deployment overruns ("Over by …" in `ReservesClient`), dashboard figures, and export values. On a fund platform, a loss displayed at raw digit-width next to peers displayed as `$5.0M` invites a direct order-of-magnitude misread. This is the same defect fixed in `analytics-utils.formatCurrency` on 2026-07-26, in the more widely used twin that was deferred at the time.
- Fix applied: Compute `sign` and `Math.abs(amount)`, scale the absolute value against the thresholds, and prefix the sign. Purely presentational — no calculated value changes, only its rendering. No existing test asserted the old negative behaviour; `tsc` and 77/77 tests pass.

### [F-002] Task completion trend bucketed into the wrong calendar day
- File: `lib/task-analytics.ts:17-30, 96-101`
- Problem: `calculateTaskMetrics` built its 30-day trend by taking a **local-midnight** `Date` and calling `.toISOString().split('T')[0]`, which converts to UTC first. For any timezone ahead of UTC — Israel is UTC+2/+3 — local midnight serialises to the *previous* day. Every bucket label was shifted back one day, and because `completed_at` was keyed in the UTC frame while the bucket was keyed in the shifted frame, tasks completed today were attributed to yesterday and today's bucket never populated.
- Fix applied: Added a `localDateKey(d)` helper that formats from `getFullYear/getMonth/getDate`, and used it for both the bucket label and the `completed_at` key so both sides share one calendar frame.

### [F-003] White cards and a white sticky column rendered in dark mode
- Files: `app/(protected)/reserves/ReservesClient.tsx:198,278,283`, `app/(protected)/network/NetworkClient.tsx:235-237`, `app/(protected)/portfolio-kpis/KPIOverviewClient.tsx:428`
- Problem: These elements hardcoded `bg-white` with no `dark:` variant, inside pages whose containers *do* switch (`dark:from-slate-950`). In dark mode the Reserves and Network summary stat rows and the Reserves "No Reserve Set" cards rendered as bright white blocks, and the Portfolio-KPI table's frozen first column rendered as a white stripe over dark rows while horizontally scrolled.
- Fix applied: Replaced the hand-rolled `bg-white rounded-lg border border-neutral-200 shadow-sm` with the existing `.card` utility (`app/globals.css:62`), which already carries the correct light/dark background, border, and shadow. Added `dark:text-white` to the two `text-neutral-900` labels inside them so the text stays legible against the now-dark background, and set the sticky KPI cell to `bg-neutral-0 dark:bg-neutral-800` to match `.card`. Scoped deliberately to cases where the correct target was unambiguous — the wider audit is [M-005].

## MANUAL ACTION REQUIRED

### [M-001] Open self-signup combined with `USING (true)` RLS policies
- Severity: **Critical**
- Category: Security
- Source: Runtime (login page "Create account") + `supabase/migrations/tasks_system.sql:143-189`, `notifications.sql:24`, `legal_entities.sql:12-13`, `deal_report_recipients.sql:12,16,20`, `add_cap_table_import.sql:60,68,76`
- Problem: Those policies are `for all to authenticated using (true) with check (true)` — they authorise **any** authenticated principal with no `team_members` membership check, unlike the core tables hardened by `rls_tighten_team_members.sql`. Prior reports rated this High on the stated assumption that open signup was disabled. The live login page renders a **"Create account"** link, so that assumption is not currently evidenced. If self-registration succeeds and yields a confirmed session, a stranger gets full read/write on `tasks` and all nine task tables, `notifications`, `legal_entities`, `deal_report_recipients`, and `cap_table_import*` — the last two holding cap-table and financial data.
- Recommended fix: (1) **Immediately** confirm in Supabase → Authentication whether signup is enabled and whether email confirmation gates session issuance; disable public signup if this is an invite-only internal tool. (2) Verify what `handle_new_user_trigger.sql` does on signup — check whether it auto-inserts a `team_members` row, which would defeat the membership predicate on the *core* tables too. (3) Replace every `using (true)` with the `exists (select 1 from team_members where id = auth.uid())` predicate already used for core tables.

### [M-002] Inline ownership calc bypasses NaN-guard & clamp (recurring)
- Severity: **Critical**
- Category: Bug (financial data integrity)
- File: `app/(protected)/companies/[id]/CompanyDetailClient.tsx:93-103` and `:386-399`
- Problem: Hand-rolls `calcCombinedOwnershipPct` but omits the per-row `Number.isFinite` guard and the final `clampOwnershipPct([0,100])`. The company detail page can display ownership >100% — inflating `currentValue` and `moic` — and **disagree with the dashboard and analytics for the same company**, which use the clamped library helper. One non-finite `ownership_percentage` from a bad import flows straight to the displayed figure. Unresolved since 2026-07-26.
- Recommended fix: Replace both inline reduces with `calcCombinedOwnershipPct(capTable, legalEntities)`. Not auto-fixed: it changes displayed financial figures, which per policy requires explicit confirmation.

### [M-003] Six pages silently swallow Supabase `.error` and render an empty portfolio
- Severity: High
- Category: Bug
- Files: `app/(protected)/dashboard/page.tsx:55-73`, `analytics/page.tsx:27-48`, `reserves/page.tsx:10-13`, `reminders/page.tsx:10-14`, `portfolio-kpis/page.tsx:10-16`
- Problem: Each destructures only `{ data }` and coerces `?? []` without inspecting `.error`. On RLS denial, expired auth, or a connectivity failure the user is shown a fully-rendered, confident **$0 / empty** view rather than an error. Reserves in particular falls through to the "No portfolio companies yet." empty state — indistinguishable from a genuinely empty fund. `companies/[id]/page.tsx:44-53` and `companies/page.tsx:29` already do this correctly, so the fix pattern is established in-repo. Scope grew from 2 pages to 5 as this audit widened.
- Recommended fix: Inspect `.error` on each query and throw so the route-level `error.tsx` renders. Not auto-fixed: it changes the failure-mode UX of the most-viewed pages, and distinguishing "empty" from "failed" is a product decision.

### [M-004] Sensitive tables still have no RLS migration in the repo (recurring)
- Severity: High
- Category: Security
- Source: Supabase — absent from `supabase/migrations/**`
- Problem: `email_integrations` (Microsoft OAuth **refresh tokens**), `company_kpis`, `safes`, `option_pools`, `share_series`, `waterfall_scenarios`, `pipeline_stages`, `task_saved_filters` are read/written by the app but have no `ENABLE ROW LEVEL SECURITY` or policy anywhere in the repo. Separately, `company_updates` and `reminders` have policies in `rls_tighten_team_members.sql:84,91` with **no accompanying `ENABLE` statement** — a policy on a table without RLS enabled is inert. Because `NEXT_PUBLIC_SUPABASE_ANON_KEY` is public by design, any table where RLS was never enabled by hand in the dashboard is reachable through PostgREST, bypassing the app's auth layer entirely. Recurring since 2026-07-05.
- Recommended fix: Run `SELECT relname, relrowsecurity FROM pg_class WHERE relname IN (...)` against prod to establish ground truth, then commit explicit `ENABLE ROW LEVEL SECURITY` + team-membership policy migrations for every table above so the state is reproducible rather than dashboard-resident.

### [M-005] Systemic dark-mode gap: 61 remaining `bg-white` with no dark variant
- Severity: Medium
- Category: UI
- Source: 61 occurrences across `app/(protected)/**` and `components/**` after F-003 (`grep -rn "bg-white" | grep -v "dark:bg"`)
- Problem: Concentrated in `PipelineBoard.tsx` (9), `contacts/ContactsClient.tsx` (6), `NetworkClient.tsx` (4 remaining), `DocumentsVaultClient.tsx` (5), `KPIOverviewClient.tsx`, `CompaniesClient.tsx` (search inputs and view-mode toggles). Dark mode is a shipped feature, so these are white inputs and toggles on dark chrome. Not all 61 are defects — `bg-white/20` and `bg-primary-500 text-white` are intentional — so a blanket replace would cause regressions.
- Recommended fix: Triage the list into (a) surfaces → `.card`, (b) form inputs → the shared input class in `lib/form-styles.ts`, (c) intentional overlays → leave. The root cause is that `lib/design-tokens.ts` and `lib/form-styles.ts` exist but are bypassed by hand-rolled class strings; routing these through the shared helpers prevents recurrence.

### [M-006] `send-deal-report` emails arbitrary body-supplied recipients
- Severity: Medium
- Category: Security
- File: `app/api/send-deal-report/route.ts:9-42`
- Problem: Gated only by `requireCronAuth` (a shared `CRON_SECRET` bearer), the route takes `recipients` from the **request body** and passes them straight into Resend's `to:` with no email-format validation, no allowlist, and no cap on recipient count. Anyone holding the cron secret can send Menomadin-branded mail with attacker-chosen content to arbitrary addresses — a branded-phishing vector. Rate limiting (5/min) bounds volume but not abuse.
- Recommended fix: Read the recipient list server-side from `deal_report_recipients` keyed by `report_date` rather than trusting the body; if body-supplied recipients must stay, validate each against a strict email regex, cap the array length, and restrict to domains present in `deal_report_recipients`.

## IMPROVEMENT IDEAS

1. **Settle the RLS question with evidence, once.** Four consecutive reports have flagged RLS while noting the migrations were authored without live-DB access. Commit a `scripts/audit-rls.ts` that connects with the service role, dumps `pg_class.relrowsecurity` and `pg_policies` for every table the app touches, and diffs against an expected manifest. Run it in CI. This turns the platform's largest recurring unknown into a pass/fail check instead of a recurring paragraph.

2. **Make the "error vs. empty" distinction structural.** M-003 keeps growing because each page hand-rolls its fetch. A `fetchOrThrow(query)` helper in `lib/supabase-server.ts` that inspects `.error` and throws would make the correct path the shortest one to write, and a lint rule banning bare `{ data }` destructuring off `supabase.from()` would stop new pages regressing.

3. **Unit-test the formatters.** F-001 and the 2026-07-26 `formatCurrency` fix were the same bug in two places, and neither had a test — while `lib/calculations.ts` maths is well covered by 77 tests. Add a table-driven suite over `fmt$$`, `fmtPct`, `fmtMultiple`, `formatCurrency` covering negatives, zero, `NaN`, `Infinity`, and threshold boundaries. These functions render every number a partner sees.

4. **Centralise date handling.** F-002 was a UTC/local frame mismatch, and `RemindersClient.tsx:35,44,54` uses the same `new Date().toISOString().split('T')[0]` idiom to compute "today" for overdue/due-today classification — so between local midnight and 03:00 Israel time, reminders are bucketed against the wrong day. Add `lib/date-utils.ts` with `todayLocal()` / `localDateKey()` and migrate all call sites.

5. **Delete the stale agent worktrees.** `.claude/worktrees/` holds six-plus abandoned copies of the repo, one with a full `node_modules`. They pollute every repo-wide `grep`/`find` (each audit must filter them out), and one contains a checked-out copy of the codebase in an unknown state. Prune them and add the path to `.gitignore` and any search-tool ignore config.
