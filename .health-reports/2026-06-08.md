### [F-001] Portfolio CSV export inflated ownership % by 100×
- File: `components/ExportPortfolioCSV.tsx:41`
- Problem: The export wrote `(c.ownershipPct * 100).toFixed(2)`. `ownershipPct`
  is already a percentage (it comes from `calcCombinedOwnershipPct`, and
  `calcCurrentValue` divides it by 100; every on-screen render uses
  `fmtPct(ownershipPct)` with no `*100`). The exported CSV therefore reported
  `1250.00` for a 12.5% stake — a wrong figure in an LP/partner-facing export on
  a financial platform.
- Fix applied: Removed the erroneous `* 100`; now exports `c.ownershipPct.toFixed(2)`,
  matching all six other call sites and the value's actual unit.
- Confidence: high — the unit was verified against `calcCurrentValue`
  (`calculations.ts:33`, divides by 100), `fmtPct` (`:518`), `ValuationChart`
  (`ownershipPct / 100 * post_money`), and `ReportsClient` (`${pct.toFixed(2)}%`).
  This corrects a display/unit error; it does not alter any calculation formula.

### [F-002] Ten server-action files performed mutations with no authentication check

  `actions/share-series.ts`, `actions/option-pools.ts`, `actions/pipeline.ts`,
  `actions/pipeline-stages.ts`, `actions/global-documents.ts`,

  flow breaks. Verified by `tsc --noEmit` (clean) and the full test suite (62/62).
- Note: this is the app-layer half of the auth perimeter. The database-layer RLS

## MANUAL ACTION REQUIRED

### [M-001] SAFE share count fabricated from a hardcoded 1,000,000 scale factor
- Severity: Critical
- Category: Bug (financial integrity)
- File: `lib/calculations.ts:339` (`buildWaterfallHolders`)
- Problem: SAFE shares are estimated as
  `Math.round((investment_amount / valuation_cap) * 1_000_000)`. This constant
  bears no relation to the company's real `share_series` share magnitudes. When
  SAFEs are mixed with real holders in `calcWaterfall`, the SAFE's equity weight is
  arbitrary, silently misallocating residual exit proceeds across all holders.
- Recommended fix: Derive SAFE shares from the same per-share basis as the cap
  table (e.g. `investment_amount / impliedPPS`), or model SAFEs on invested-amount
  preference rather than fabricated shares. Treat as a calculation change requiring
  review.

### [M-002] Ownership read by array position — and two ownership functions disagree
- Severity: Critical
- Category: Bug (financial integrity)
- File: `lib/calculations.ts:47-51` (`getFundOwnershipPct`); divergence at
  `app/(protected)/reports/lp-update/page.tsx:49` vs `app/(protected)/dashboard/page.tsx:100`
- Problem: `getFundOwnershipPct` returns `capTable[capTable.length - 1].ownership_percentage`
  — it assumes the fund row is always inserted last, and Supabase does not guarantee
  read order without an `ORDER BY`. It can silently read a *different* shareholder's
  ownership %, corrupting MOIC/FMV. Worse, the **dashboard** uses
  `calcCombinedOwnershipPct` (sums across legal entities) while the **LP report** uses
  `getFundOwnershipPct`, so the same company can show different ownership / current
  value / MOIC on the two screens.
- Recommended fix: Select the fund row(s) by matching shareholder name / legal-entity
  alias (as `calcCombinedOwnershipPct` does), not by array position; use one ownership
  function consistently across dashboard, analytics, and the LP report.

### [M-003] XIRR has no convergence verification and silently discards results
- Severity: Critical
- Category: Bug (financial integrity)
- File: `lib/calculations.ts:88-122` (`calcXIRR`)
- Problem: Newton-Raphson returns `null` on non-convergence and on `r > 100`
  (10,000% IRR) with no NPV residual check and no bisection fallback. For
  multi-sign cash-flow streams it can converge to a spurious/local root; legitimately
  high early-stage IRRs above the cap are dropped to `null` (shown as "no IRR").
- Recommended fix: Verify `npv(result) ≈ 0` at the returned rate and fall back to
  bracketed bisection before returning `null`; reconsider the upper bound. Calculation
  change requiring review.

### [M-004] Anti-dilution conversion-price adjustment doesn't validate inputs
- Severity: Critical
- Category: Bug (financial integrity)
- File: `lib/calculations.ts:255-269` (`calcAntiDilutionBroadBasedWA`)
- Problem: The `a + c === 0` guard exists, but `newPPS = 0` or negative (or negative
  `newSharesIssued`) flows through and yields a mathematically wrong / possibly
  negative adjusted conversion price.
- Recommended fix: Validate `newPPS > 0`, `newSharesIssued >= 0`,
  `totalSharesPreRound >= 0`; return `originalPPS` (no adjustment) otherwise.

### [M-005] share_series & option_pools accept unvalidated numeric inputs
- Severity: Critical
- Category: Bug (financial integrity)
- File: `actions/share-series.ts`, `actions/option-pools.ts` (all mutations)
- Problem: Neither validates `shares`, `price_per_share`, `liquidation_pref_mult`,
  `conversion_ratio`, `shares_authorized`, etc. A negative/non-finite value flows
  into `calcWaterfall` (`shares * conversionRatio`) and `calcFullyDilutedShares`,
  producing NaN/negative denominators and corrupt ownership %.
- Recommended fix: Apply `isInvalidMetric` (from `lib/validation`) to all numeric
  fields, matching `actions/kpis.ts` / `rounds.ts` / `safes.ts`. (Auth guard already
  added in F-002; validation is the remaining piece.)

### [M-006] `c.moic || 1` hides total-loss companies from underperformers
- Severity: Medium
- Category: Bug (financial)
- File: `lib/analytics-utils.ts:103,119` (`getTopPerformers` / `getUnderperformers`)
- Problem: `c.moic || 1` coerces a legitimate MOIC of `0` (total write-off) to `1`
  (break-even); `getUnderperformers`'s `filter(c => c.moic < 1)` then excludes those
  wiped-out companies entirely.
- Recommended fix: Use `c.moic ?? 1` (nullish coalescing) instead of `||`.

### [M-007] Analytics page shows "N/A" for a genuine 0% portfolio IRR

- Severity: High
- Category: Security

### [M-010] Several financial/document tables remain readable/writable by ANY authenticated user

### [M-011] `analyze-deck` fetches a user-supplied URL with no size cap
- Severity: High
- Category: Security / Performance
- File: `app/api/pipeline/analyze-deck/route.ts:21-29`
- Problem: Unlike `/api/extract` (which uses `fetchWithSizeCap`), this route does a
  bare `fetch(deck_url)` → `arrayBuffer()` with no Content-Length/byte cap before
  base64-encoding and shipping to Anthropic. Although the host is pinned to Supabase

  and incur unbounded LLM cost.
- Recommended fix: Reuse `fetchWithSizeCap` with a PDF byte cap (e.g. 20 MB) before
  reading the body.

## IMPROVEMENT IDEAS
1. **Consolidate portfolio math into one source of truth** (addresses M-002, M-022).
   Extract `computeCompanyMetrics()` + `buildPortfolioCashFlows()` into
   `lib/calculations.ts` and have the dashboard, analytics, and LP report all call it.
   This removes the dashboard-vs-LP-report ownership divergence in one move and makes
   the financial figures testable in isolation — the highest-leverage change here.
2. **Add unit tests for the financial primitives.** There are already 62 passing tests;
   extend them to cover `calcXIRR` convergence/edge cases (M-003), anti-dilution
   validation (M-004), the SAFE share model (M-001), and `getUnderperformers` with
   `moic = 0` (M-006). These are exactly the functions where a silent error is most
   costly and least visible.
3. **Close the RLS perimeter and disable public sign-ups** (M-009, M-010). The app-layer
   auth guards added today are defense-in-depth; the database is the real perimeter.
   Extend the `team_members` gate to the remaining tables, ship the missing
   `email_integrations` policy as a committed migration, and turn off self-registration
   in Supabase Auth so the visible "Create account" link can't be abused.
4. **Standardize page-level data loading** (M-012, M-017, M-020). Adopt one pattern:
   projected-column queries + row limit + an error card on `res.error` + an
   `error.tsx` boundary. Several pages already do this well (pipeline, documents,
   companies/[id]); making it uniform removes a whole class of silent-failure and
   performance issues at once.
5. **Add input validation to the cap-table actions** (M-005). `share_series` and
   `option_pools` are the only financial-write paths still missing `isInvalidMetric`
   guards, and they feed the waterfall directly — a single negative `conversion_ratio`
   corrupts every ownership figure downstream.
