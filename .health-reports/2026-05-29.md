### [F-002] M-042: SAFE conversion idempotency — refuse double-conversion at both TS and SQL layers
- Files:
  - `actions/safes.ts:118-122` — after fetching the SAFE, early-return `'This SAFE has already been converted.'` when `safe.status === 'converted'`
  - `supabase/migrations/convert_safe_rpc.sql` — `update safes set ... where id = p_safe_id AND status = 'unconverted' returning company_id`. When no row is updated, the function raises `'SAFE % is already converted or does not exist'` before any cap_table insert
- Problem: Previous Critical, day 2. Yesterday's RPC was atomic but not idempotent — a retry/double-click/server-action re-trigger would update the (already-converted) SAFE again and insert a **second** cap_table row, double-counting that holder's ownership across every downstream waterfall.
- Fix applied: The SQL filter on `status = 'unconverted'` is the authoritative guard (atomically impossible to double-insert). The TS-layer check exists only for a friendlier UI error message before the RPC fires. Defense in depth: even if a future caller skips the TS guard, the RPC refuses. **Note**: the migration file needs to be re-applied to production Supabase to take effect.

### [F-003] M-043: LP-report ownership column now filters to fund-held cap_table rows
- Files:

### [F-004] M-027: AES-256-GCM encryption-at-rest for OAuth tokens (backward-compatible rollout)
- Files:
  - `lib/token-crypto.ts` (new) — `encryptToken(plain)` / `decryptToken(stored)` with format `enc:v1:<base64iv>:<base64tag>:<base64ciphertext>` packed into the existing TEXT column (no schema migration)
  - `app/api/auth/microsoft/callback/route.ts:90-95` — encrypts both `access_token` and `refresh_token` before upserting
  - `lib/microsoft-graph.ts:45, 70-75, 95` — decrypts the stored refresh_token before exchanging it; re-encrypts both new tokens on refresh; decrypts the stored access_token before handing it to callers
- Problem: Previous High-severity, day 11. Refresh tokens are ~90-day sliding capabilities; a Postgres backup leak or RLS regression would expose inbox access for the remaining token lifetime.
- Fix applied: AES-256-GCM keyed by `EMAIL_TOKEN_KEY` (SHA-256-hashed to 32 bytes so any passphrase length works). Backward compat in three directions:
  1. Operator hasn't set `EMAIL_TOKEN_KEY` yet → `encryptToken` returns plaintext (one-time warning per cold-start, no surprise lock-outs)
  2. Legacy plaintext rows in DB → `decryptToken` detects the absence of the `enc:v1:` prefix and passes through unchanged
  3. Encrypted rows in DB but key was lost → `decryptToken` returns null, caller treats as "no token" and forces a fresh OAuth flow (no crash)
- **Action required outside code**: set `EMAIL_TOKEN_KEY` in Vercel production env (any high-entropy string — it'll be SHA-256-d to a 32-byte key). Existing rows re-encrypt automatically the next time a user reconnects Outlook or the refresh-token grant fires.

### [F-005] M-034: per-type upload size caps on `/api/extract`
- File: `app/api/extract/route.ts:13-45, 82-88`
- Problem: Previous Medium, day 4. `fetch(file_url).arrayBuffer()` was unbounded — a malicious or buggy caller could pass a `file_url` to a multi-hundred-MB file and force the route to allocate the buffer + base64 expansion before failing.
- Fix applied: New `fetchWithSizeCap(url, maxBytes)` helper that checks `Content-Length` first (short-circuits before reading the body) and re-checks `byteLength` after the read for backends that don't send Content-Length. Caps per file type: PDF 20MB, Image 5MB, Spreadsheet 10MB, Text 5MB. Returns HTTP 413 on overflow. Mirrors the existing pattern at `app/api/import/route.ts:51-54`.
