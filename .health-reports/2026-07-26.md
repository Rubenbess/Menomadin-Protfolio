## FIXED ISSUES

### [F-001] formatCurrency did not scale negative values
- File: `lib/analytics-utils.ts:129-137`
- Problem: Negative amounts fell through both `>= 1_000_000` and `>= 1_000` branches, rendering a net loss of -$5,000,000 as `$-5000000` instead of `-$5.0M`. On a fund dashboard, unscaled/garbled loss figures are misleading.
- Fix applied: Compute `sign` and `Math.abs(value)`, scale the absolute value, and prefix the sign — so negatives render as `-$5.0M` / `-$5.0K` consistently. Verified `tsc --noEmit` still passes. (Note: `fmt$$` in `lib/calculations.ts:547` shares the trait — left untouched as it is financial-calc-adjacent; see M-005.)

## MANUAL ACTION REQUIRED

### [M-001] Sensitive tables have no RLS migration in the repo
- Severity: Critical
- Category: Security
- Source: Supabase — `supabase/migrations/**`, `schema.sql`
- Problem: `email_integrations` (stores Microsoft OAuth **refresh tokens**), `company_kpis`, `safes`, `option_pools`, `share_series`, `waterfall_scenarios`, `pipeline_stages`, `task_saved_filters` are read/written by the app but have no `ENABLE ROW LEVEL SECURITY` or policy anywhere in the repo. The `NEXT_PUBLIC_SUPABASE_ANON_KEY` is public by design, so if RLS was never enabled manually in the Supabase dashboard, these tables are readable/writable by anyone via PostgREST, bypassing all app-layer auth. Crown-jewel data (OAuth tokens, cap tables, KPIs). Recurring (matches M-006 in 2026-07-05).
- Recommended fix: In the live DB, run `SELECT relname, relrowsecurity FROM pg_class WHERE relname IN (...)` to confirm current state. Commit explicit migrations enabling RLS + team-membership policies for each table.

### [M-002] Task-system tables use blanket `USING (true)`
- Severity: High
- Category: Security
- Source: `supabase/migrations/tasks_system.sql:143-189`
- Problem: `tasks`, `task_assignees`, `task_comments`, `task_activities`, `task_attachments`, `task_labels`, `task_label_links`, `task_recurrence_rules`, `task_automation_rules` all use `for all to authenticated using (true) with check (true)` — granting full access to any authenticated principal, including a signed-up user with no `team_members` row. Unlike core tables (upgraded by `rls_tighten_team_members.sql`).
- Recommended fix: Replace `using(true)` with the `exists (select 1 from team_members where id = auth.uid())` predicate used for core tables.

### [M-003] `USING (true)` on notifications / legal_entities / deal_report_recipients / cap_table_import*
- Severity: High
- Category: Security
- Source: `notifications.sql:24`, `legal_entities.sql:12-13`, `deal_report_recipients.sql:12,16,20`, `add_cap_table_import.sql:60,68,76`
- Problem: Same "any authenticated user, no membership check" pattern; `legal_entities` and `cap_table_import*` hold financial/cap-table data. Relies entirely on open signup being disabled.
- Recommended fix: Apply the `team_members` membership predicate to these policies.

### [M-004] Policies present but RLS-enable statement missing (inert policies)

### [M-005] Inline ownership calc bypasses NaN-guard & clamp — financial inconsistency
- Severity: High
- Category: Bug (financial data integrity)
- File: `app/(protected)/companies/[id]/CompanyDetailClient.tsx:93-103` (and entity-level `:386-399`)
- Problem: Hand-rolls `calcCombinedOwnershipPct` but omits the per-row `Number.isFinite` guard and the final `clampOwnershipPct([0,100])`. The company detail page can show ownership >100% (inflating `currentValue`/`moic`) and **disagree with the dashboard/analytics** for the same company, which use the clamped library helper. A bad-import non-finite `ownership_percentage` row flows straight into the displayed value.
- Recommended fix: Replace both inline reduces with `calcCombinedOwnershipPct(capTable, legalEntities)`. Flagged rather than auto-fixed per policy (alters displayed financial figures — needs confirmation).
