## MANUAL ACTION REQUIRED

### [M-001] `roles` and `table_permissions` tables have RLS disabled — privilege escalation
- Severity: **Critical**
- Category: Security
- File or Source: `supabase/migrations/table_permissions.sql` (Supabase schema)
- Problem: Of the 29 tables created across `schema.sql` and `supabase/migrations/`, 27 call `ENABLE ROW LEVEL SECURITY`. The two that do not are `roles` and `table_permissions` — the tables that *define* the RBAC matrix. No `GRANT` or `REVOKE` statement exists anywhere in the migration set, so Supabase's default grants to `anon` and `authenticated` apply unmodified. The whole access-control model routes through `can_perform_action()`, which reads `table_permissions` directly; every policy on `companies`, `contacts`, `rounds`, `investments`, `cap_table`, `reserves`, `documents` and `pipeline` delegates to it. A user provisioned as `viewer` or `associate` can therefore issue, with nothing but the public anon key from the browser, `update table_permissions set can_delete = true where role_name = 'viewer'` and immediately gain delete rights over the entire investment and cap-table dataset. They can also read the full permission matrix to find the weakest role. This is the single highest-risk finding on the platform.
- Recommended fix: add a migration that enables RLS on both tables and grants read-only access to authenticated users, with no client-side write path:
  ```sql
  ALTER TABLE roles ENABLE ROW LEVEL SECURITY;
  ALTER TABLE table_permissions ENABLE ROW LEVEL SECURITY;
  CREATE POLICY "roles_read" ON roles FOR SELECT TO authenticated USING (true);
  CREATE POLICY "table_permissions_read" ON table_permissions FOR SELECT TO authenticated USING (true);
  -- No INSERT/UPDATE/DELETE policy: permission changes go through a
  -- service-role admin path only.
  ```
  Then verify in the Supabase dashboard that no `viewer`-role session can write to either table. Not auto-fixed: Phase 3 rule 3 forbids this agent from altering RLS policies or migrations.

### [M-002] `can_perform_action` returns NULL for any table with no permission row
- Severity: High
- Category: Security / Bug
- File or Source: `supabase/migrations/table_permissions.sql:64-78`
- Problem: `can_perform_action()` is a bare `SELECT ... FROM table_permissions WHERE role_name = get_user_role() AND table_name = p_table_name`. If no row matches it returns NULL, and an RLS policy of `USING (NULL)` evaluates as deny — which is the safe direction, but it is accidental rather than designed. The `table_name` CHECK constraint only permits `('companies','contacts','tasks','documents')`, so any future policy written against a table name outside that set silently denies all access to every user with no error raised anywhere. Conversely, if a `table_permissions` row is ever deleted, the corresponding table goes dark platform-wide with no diagnostic. Related: the `documents` policies delegate to `can_perform_action('companies', ...)` even though a `documents` permission row exists and is populated — so the `documents` row in the matrix is dead configuration that an admin editing permissions would reasonably expect to take effect, and it does not.
- Recommended fix: make the deny explicit with `COALESCE(..., false)` and add a fallback branch so a missing row is a logged, intentional deny. Point the `documents` policies at `can_perform_action('documents', ...)` so the matrix row an admin sees is the one enforced, or drop the unused row.

### [M-003] ESLint is not configured — `npm run lint` cannot run
- Severity: Medium
- Category: Code Quality
- File or Source: repository root (`package.json:8`)
- Problem: `npm run lint` invokes `next lint`, which finds no `.eslintrc*` or `eslint.config.*` anywhere in the repo and drops into an interactive "How would you like to configure ESLint?" setup prompt. In CI or any non-interactive context that call hangs or fails. The project therefore has no lint gate at all: no unused-import detection, no exhaustive-deps checking on hooks, no accessibility rules. `next lint` is also deprecated and removed in Next.js 16, while the project is on `next ^15.1.0`.
- Recommended fix: migrate to the ESLint CLI with `npx @next/codemod@canary next-lint-to-eslint-cli .`, adopt `next/core-web-vitals`, and change the `lint` script to `eslint .`. Expect an initial batch of warnings (notably `@next/next/no-img-element` for the 8 logo tags and `react-hooks/exhaustive-deps`) — triage those in a dedicated pass rather than mixing them into a health-check commit. Not auto-fixed: adding a lint config will surface a wave of new errors and could break a CI gate, which is a decision for the team.

### [M-006] 68 unbounded `.select('*')` queries with no pagination
- Severity: Medium
- Category: Performance
- File or Source: `app/` and `actions/` (68 occurrences)
- Problem: the codebase issues 68 `.select('*')` calls with no `.limit()` or `.range()`. Each pulls every column of every row the RLS policy permits. At today's portfolio size this is invisible, but it scales linearly with the deal pipeline and the activity log — `activities` in particular is append-only audit data that grows without bound, and any page selecting `*` from it will degrade steadily and silently until it times out.
- Recommended fix: replace `select('*')` with explicit column lists on the hot paths (portfolio table, pipeline board, activity feed) and add `.range()` pagination to any query over an append-only table. Prioritise `activities` and `company_kpis` since both grow monotonically.

### [M-007] 13 `as any` casts, 5 of them on Supabase data crossing a component boundary
- Severity: Low
- Category: Code Quality
- File or Source: `app/(protected)/profile/page.tsx:41-45`, plus `TaskEditModal.tsx:150,166`, `TaskTemplates.tsx:207`, `task-dependencies.ts:82,96`, `ListPageHeader.tsx:38`, `TaskCommentInput.tsx:111`

Given the memory note that `pipeline.status` uses capitalized stage names while stale lowercase references persist in the codebase, `deals as any[]` is precisely the cast that would hide such a mismatch. - Recommended fix: type the `profile/page.tsx` props against the `lib/types.ts` interfaces and fix whatever mismatches surface. For the select handlers, narrow with a validating cast (`value as TaskStatus` behind a runtime membership check) rather than `any`.

### [M-008] Public founder-update rate limit is keyed per token
- Severity: Low
- Category: Security
- File or Source: `actions/founder-updates.ts:35`
- Problem: `checkRateLimit('founder-update:' + data.token, 5, 60_000)` buckets by the submitted token, so every distinct guess gets a fresh allowance — the limiter caps abuse of a *known* link but does nothing against enumeration. Separately, `app/updates/[token]/page.tsx` performs a service-role lookup against `companies.update_token` with no rate limit at all. In practice the risk is negligible because tokens are `crypto.randomUUID()` (122 bits of entropy, not brute-forceable), which is why this is Low rather than High — but the limiter does not provide the protection its placement implies.
- Recommended fix: add a second IP-keyed bucket alongside the token bucket (e.g. `checkRateLimit('founder-update-ip:' + ip, 20, 60_000)`) and apply the same to the token page's lookup. Note that `lib/rate-limit.ts` is in-process, so on Vercel's serverless runtime the counter resets per cold start and is not shared across concurrent instances — treat it as a speed bump, not a control, and document that limitation in the file.

RLS is the one layer with no compile-time or unit-test coverage today, and it is the layer holding the financial data.

Property-based tests asserting that waterfall payouts always sum to exactly the exit proceeds, and that ownership percentages sum to 100, would catch the class of bug those comments describe.

3. **Resolve the `pipeline.status` casing drift.** Stale lowercase status references persist against a capitalized-stage schema. Define the stage names once as a `const` union in `lib/types.ts`, derive both the UI labels and the query filters from it, and remove the `as any` at `profile/page.tsx:42` so `tsc` enforces it. Right now a mismatched filter fails silently by returning zero deals — on a pipeline board that reads as "no deals this stage", not as a bug.

4. **Get the lint gate running (M-003) before the Next.js 16 upgrade forces it.** `next lint` is already deprecated; doing the codemod now is a contained task, whereas doing it under an upgrade means untangling lint failures and framework breakage at once. 5. **Add route-level `loading.tsx` and column-scoped selects together (M-005 + M-006).** These are the same user-facing symptom — a dashboard that feels slow as data grows — attacked from both ends. Doing the four heaviest routes as one focused pass would give the most visible responsiveness win available right now, with no behavioural risk.
