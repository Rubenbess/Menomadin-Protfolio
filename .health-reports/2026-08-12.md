## FIXED ISSUES

### [F-001] Report/export filenames and CSV date cells used UTC instead of local calendar date
- Files:
  - `lib/csv-export.ts` (date cell formatting + 4 export filenames)
  - `lib/pdf-export.ts` (portfolio PDF filename)
  - `components/ExportPortfolioCSV.tsx` (portfolio CSV filename)
  - `app/(protected)/reports/lp-update/LPReportClient.tsx` (LP update PDF filename)
- Problem: these client-side paths used `new Date().toISOString().split('T')[0]`, which
  converts to UTC before slicing. Israel is UTC+2/+3, so between local midnight and
  02:00/03:00 the idiom yields *yesterday*. Effect: an LP-facing PDF or a cap-table CSV
  exported late at night is stamped with the wrong calendar date, and `formatValue()`
  wrote Date cells one day early into exported CSVs. On LP-facing and audit-trail output,
  a date that disagrees with the day the file was produced is a real credibility problem.
- Fix applied: routed all four through the existing `localDateKey()` / `todayLocal()`
  helpers in `lib/date-utils.ts` — the same helpers the in-flight fix already applies to
  `lib/task-analytics.ts` and `components/Sidebar.tsx`. This completes that fix across
  the client-side surface. No calculation logic touched. tsc + 105 tests still green.

### [F-002] `calcFullyDilutedShares` doc comment overstated what the function computes
- File: `lib/calculations.ts`
- Problem: the comment read "issued shares + option pool reserved + SAFE shares
  (estimated)", but the implementation only sums issued shares and option pools — it has
  never included SAFEs. On a cap-table platform this invites a caller to trust the FD
  denominator as SAFE-inclusive, understating dilution for any company holding
  unconverted SAFEs.
- Fix applied: corrected the comment to state what the code does, plus an explicit note
  that SAFEs are excluded and that `buildWaterfallHolders` is the path that does estimate
  SAFE share counts. Comment-only — zero behaviour change. The arithmetic was not altered,
  because whether FD should include SAFEs is a modelling decision, not a bug fix.

## MANUAL ACTION REQUIRED

### [M-001] Ownership-percentage unit inference can silently introduce a 100x error
- Severity: **Critical**
- Category: Bug / Financial data integrity
- File: `app/api/import/route.ts:30-34` (`pct()`), consumed at line 223 for
  `row['Ownership Percentage']`
- Problem: `pct()` guesses whether a spreadsheet cell means a fraction or a percent:
  `return parseFloat((n < 1 ? n * 100 : n).toFixed(4))`. A genuine ownership of **0.5%**
  written as `0.5` is read as **50%** — a 100x overstatement. Ownership % feeds
  `calcCurrentValue()` (`ownershipPct / 100 * postMoney`), which feeds company value,
  portfolio MOIC, TVPI and XIRR. The values are also clamped to `[0, 100]`, so a corrupted
  50% looks perfectly plausible and will not trip any guard. This route is the
  *destructive* bulk import — it deletes and re-inserts rounds/investments/cap_table rows
  for each company in the workbook — so a bad inference overwrites correct history.
  Sub-1% positions are entirely normal for an early-stage impact fund, so this is not a
  hypothetical input.
- Recommended fix: stop inferring. Either (a) require an explicit unit declaration per
  import (a "percentages are expressed as: percent / fraction" selector, applied to the
  whole sheet), or (b) reject ambiguous values — any `0 < n < 1` — into the existing
  dry-run preview as a row-level error the user must resolve before writing. Option (b)
  composes with the `dryRun=true` preview already in this route. Not auto-fixed: this
  changes financial import semantics and needs the actual spreadsheet convention confirmed.

### [M-002] No timezone anchor for server-side dates — the `date-utils` fix does not cover server code
- Severity: **High**
- Category: Bug / Financial data integrity
- Files: `actions/task-automations.ts:143`, `actions/task-recurrence.ts:101,118,119`
- Problem: these write `due_date` / `next_occurrence` / `last_generated` by doing local
  date arithmetic (`setDate`, `setMonth`) and then serialising with
  `toISOString().split('T')[0]`. Swapping in `localDateKey()` **would not fix these** —
  Vercel serverless runs in UTC, so "local" and UTC are the same thing there. The real
  defect is that server-side code has no notion of the fund's calendar at all: when an
  Israel user triggers an automation at 01:30 local (22:30 UTC the previous day), a
  "due in 7 days" task lands one day earlier than the user intends. `lib/date-utils.ts`
  correctly documents and solves the *client* case only; the server case is currently
  unaddressed and undocumented, which is the more dangerous state because the helper's
  existence implies coverage.
- Recommended fix: add a timezone-anchored helper to `lib/date-utils.ts` — e.g.
  `jerusalemDateKey(d)` built on `Intl.DateTimeFormat('en-CA', { timeZone: 'Asia/Jerusalem' })`
  — and use it for every server-side value that means a calendar day. Extend the doc block
  at the top of `date-utils.ts` to state explicitly that `localDateKey` is client-only and
  why. Add a test that fakes a 22:30-UTC clock and asserts the Jerusalem date is the next day.

### [M-003] Bulk import fabricates a first-investment date when the cell is blank
- Severity: Medium
- Category: Bug / Financial data integrity
- File: `app/api/import/route.ts:8-16` (`toDate()`), consumed at line 217 for
  `row['Date of First Investment']`
- Problem: `if (!val) return new Date().toISOString().slice(0, 10)` — a missing investment
  date silently becomes *today*. That is invented financial data written into the record
  with no marker, and it directly distorts XIRR, whose cash-flow timing depends on
  investment dates. A holding from 2019 imported with a blank date is dated 2026-08-12,
  compressing its holding period to zero.
- Recommended fix: return `null` and let the column be nullable, or surface the blank as a
  dry-run validation error the user must fill in. Never substitute a plausible-looking date
  for a missing one on a financial record.

### [M-004] ESLint is a dependency but has no configuration — `npm run lint` does not run
- Severity: Medium
- Category: Code Quality
- File: `package.json` (`"lint": "next lint"`; `eslint ^8`, `eslint-config-next ^15`), no

  the script to `eslint .`. Expect a substantial first-run backlog — triage it, don't
  blanket-disable.

### [M-005] Reminder digest cron defines "today" in UTC
- Severity: Low
- Category: Bug
- File: `app/api/cron/reminders/route.ts:36`
- Problem: `const today = new Date().toISOString().split('T')[0]`, then
  `.lte('due_date', today)`. **Currently correct**: `vercel.json` schedules this at
  `0 7 * * *` (07:00 UTC = 10:00 Israel), where the UTC and Israel dates agree. But the
  correctness depends entirely on the cron schedule, with nothing recording that coupling.
  Rescheduling the digest to any time before 02:00/03:00 Israel would silently start
  omitting reminders that are due that day.
- Recommended fix: use the `jerusalemDateKey` helper from M-002 so the query is correct at
  any schedule, and drop a one-line comment noting that the digest's "today" means the
  fund's calendar day. Flagged Low only because it is not currently misbehaving.

### [M-006] `calcWaterfall` returns a hardcoded empty `warnings` array
- Severity: Low
- Category: Bug / API design
- File: `lib/calculations.ts` (`calcWaterfall`, final `return`)
- Problem: the function's return type advertises `warnings: []` but always returns an empty
  literal. The real data-quality warnings (excluded uncapped SAFEs, zero-amount SAFEs) come

## IMPROVEMENT IDEAS

1. **Add a timezone-anchored date layer and ban the raw idiom.** M-002 and M-005 are the
   same root cause, and `lib/date-utils.ts` is already two-thirds of the answer. Finish it
   with a `jerusalemDateKey` for server code, then add a lint rule (once M-004 gives you a
   working ESLint) banning `toISOString().split('T')[0]` outside `date-utils.ts`. This
   class of bug has now produced findings on multiple days; a lint rule ends it permanently.

2. **Make the bulk importer fail loudly instead of guessing.** M-001 and M-003 are both the
   importer inventing data rather than refusing it. The `dryRun=true` preview is the right
   place to fix this: promote every inference — ambiguous percentage, blank date, inferred
   entity mandate (`mandateIsInferred` is already exported from `lib/entities.ts` and looks
   unused by this route) — into an explicit row-level warning list the user must
   acknowledge. For a destructive import on a financial dataset, a refusal is always
   cheaper than a silent 100x error.

3. **Get the RLS audit onto a footing an unattended run can actually check.** Commit a
   script that dumps `pg_policies` and asserts an expected-policy snapshot, runnable with
   the service-role key. That converts the perpetually-deferred "review RLS" item into a
   pass/fail check this health check can run daily, and it would catch a policy regression
   the day it lands rather than whenever someone next looks.

4. **Grow the test suite around the money paths.** 105 tests passing is a real asset, and
   `lib/calculations.ts` shows heavy, well-commented remediation history — write-off
   valuation, positional cap-table reads, DPI honesty, negative-currency formatting. Each
   of those was a real bug. Lock them in with property-based tests: ownership always in
   `[0, 100]`, MOIC/TVPI never `NaN`/`Infinity`, waterfall payouts summing to exit value.
   The waterfall in particular is the most intricate logic in the codebase and the least
   directly covered.

5. **Set up a weekly commit-hygiene checkpoint.** M-007 shows a full day's worth of good
   fixes undeployed. Whatever ships these fixes to production is the step that actually
   delivers the value; a Friday "commit and deploy pending fixes" habit would keep the live
   platform in sync with the remediation work already done.
