### [M-008] `unlinkContactFromCompany` ignores the supplied `companyId`
- Severity: **Medium**
- Category: Bug
- File: [actions/contacts.ts:91-98](actions/contacts.ts:91)
- Problem: The action accepts `(contactId, companyId)` but only uses `companyId` for `revalidatePath`. The database `update` is `from('contacts').update({ company_id: null }).eq('id', contactId)` — there's no `.eq('company_id', companyId)` guard. Net effect: if the React tree shows a stale or wrong `companyId` (e.g., the contact was just re-linked elsewhere in another tab), calling `unlink` still detaches the contact, but the toast/UI will revalidate the path of a company that didn't own the contact anymore. The function name implies a two-row precondition ("unlink THIS contact FROM THIS company") that the SQL doesn't enforce. This is also a contract violation for any future caller that expects unlink to be idempotent/no-op when the link isn't there.
- Recommended fix: Add `.eq('company_id', companyId)` to the update. Optionally check the returned row count and short-circuit if zero (`.select()` to confirm). One-line change; needs no schema work. Pairs with the auto-fixed error-toast (F-002) — once the action fails fast on stale state, the user sees the toast and knows to refresh.

### [M-011] Round-delete relies on undocumented FK cascade for child investments
- Severity: **Medium**
- Category: Bug / data integrity
- Files: [actions/rounds.ts:32-37](actions/rounds.ts:32), [app/(protected)/companies/[id]/CompanyDetailClient.tsx:694-700](app/(protected)/companies/[id]/CompanyDetailClient.tsx:694)
- Problem: The button copy is explicit ("Delete this round **and all its investments**?"), but `deleteRound` does a single `from('rounds').delete().eq('id', id)` with no accompanying child-row delete. This works if and only if the `investments.round_id` FK is declared `ON DELETE CASCADE`. The repo does not contain a base-schema migration for `rounds` or `investments` (the `supabase/migrations/` tree only has feature-additive SQL — tasks, contacts, pipeline, RLS, etc.), so the cascade behavior is implicit / Studio-managed. If the FK is `ON DELETE NO ACTION` (the Postgres default), the round delete will fail with a FK violation at runtime — the user now sees the toast added by F-002, but the underlying claim of the button is wrong.
- Recommended fix: Either (a) confirm the FK in Studio is `ON DELETE CASCADE` and add a tiny migration that codifies the constraint so it's reviewable in PRs, or (b) make `deleteRound` perform the two-step delete inside a transaction (`investments` where `round_id = $1`, then `rounds` where `id = $1`). Option (b) is the more honest path because it makes the "and all its investments" copy true at the application layer.
