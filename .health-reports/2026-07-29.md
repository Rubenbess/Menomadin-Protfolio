## FIXED ISSUES

### [F-001] Sidebar overdue-task badge undercounted every hour of the day
- File: `components/Sidebar.tsx:84-86`
- Problem: `TasksBadge` built its cutoff as `new Date()` → `setHours(0,0,0,0)` → `.toISOString().split('T')[0]`. Pinning a Date to *local* midnight and then serialising it as *UTC* yields the previous calendar day at **every hour of the day** in Israel (UTC+2/+3) — not merely in an early-morning window. The query `.lt('due_date', todayString)` therefore excluded everything due yesterday, so a task became visible in the overdue badge only after it was two days late. This is the platform's only ambient signal that work has slipped, and it was silently one day slow, permanently. `ReminderBadge` at `:62` had the milder instant-based variant of the same bug (wrong between local midnight and 02:00/03:00).
- Fix applied: Both badges now call `todayLocal()` from the new `lib/date-utils.ts`. Comment added at the `TasksBadge` site recording why `setHours(0,0,0,0)` + `toISOString()` is the wrong pairing, since the code reads as though it were deliberately normalising.

### [F-002] Reminder status misclassified overdue items as "Today"
- File: `app/(protected)/reminders/RemindersClient.tsx:35,44-45,54`
- Problem: `getStatus`, `fmtDue`, and `daysUntil` each computed "today" with `new Date().toISOString().split('T')[0]`. Between local midnight and 02:00/03:00 Israel time that string is *yesterday*, which shifts the entire classification by one day: genuinely overdue items render with the neutral **"Today"** badge, and items actually due today are demoted to **"Upcoming"** and drop out of the urgent filters. `daysUntil` was off by one over the same window, and `fmtDue` labelled tomorrow as "Today".
- Fix applied: All four sites now use `todayLocal()` / `addDaysLocal(1)`. Pure date-frame correction — no change to which reminders are fetched or to any threshold.

### [F-003] Extracted `lib/date-utils.ts` and converted six date-input prefills
- Files: new `lib/date-utils.ts`, new `__tests__/date-utils.test.ts`, `lib/task-analytics.ts:17-30`, `components/forms/KPIForm.tsx`, `components/forms/ReminderForm.tsx`, `components/forms/UpdateForm.tsx`, `app/updates/[token]/FounderUpdateForm.tsx`, `app/(protected)/contacts/ContactsClient.tsx`, `app/(protected)/reports/ReportsClient.tsx`
- Problem: The same UTC-serialisation idiom appeared at 30 call sites. Six of them prefill a `<input type="date">` with "today" — the KPI entry form, reminder due date, company update date, the **public founder-update form**, contact interaction date, and the report date. Each would prefill *yesterday* during the early-morning window, and because a prefilled field is the one users are least likely to check, a KPI or founder update silently lands on the wrong day. On a platform where KPI and update rows are keyed and charted by date, that is a data-integrity issue, not a cosmetic one. The founder form is worst-affected: it is used by external founders in arbitrary timezones.
- Fix applied: Created `lib/date-utils.ts` exporting `localDateKey(d)`, `todayLocal()`, and `addDaysLocal(n, from?)`, with a header comment documenting exactly why `toISOString()` is wrong here and when it is still appropriate. Migrated the six prefills, and removed the duplicate private `localDateKey` added to `lib/task-analytics.ts` yesterday so there is one implementation. Added `__tests__/date-utils.test.ts` — 9 tests covering local midnight, whole-day stability, zero-padding, month/year/leap-day boundaries; every case fails under the old idiom at UTC+n. Suite went 96 → 105, all passing. Deliberately **not** converted: `lib/csv-export.ts` and `lib/pdf-export.ts` filename stamps (cosmetic), and `app/api/**` server-side uses (see [M-005] — a server timezone decision, not a mechanical swap).

## MANUAL ACTION REQUIRED

### [M-001] `USING (true)` RLS policies grant any authenticated principal full access (downgraded)
- Severity: **High** (was Critical on 2026-07-28)
- Category: Security
- Source: `supabase/migrations/tasks_system.sql:143-189`, `notifications.sql:24`, `legal_entities.sql:12-13`, `deal_report_recipients.sql:12,16,20`, `add_cap_table_import.sql:60,68,76`
- Problem: These policies are `for all to authenticated using (true) with check (true)` — no `team_members` membership check, unlike the core tables hardened by `rls_tighten_team_members.sql`. Any authenticated principal gets full read/write on `tasks` and all nine task tables, `notifications`, `legal_entities`, `deal_report_recipients`, and `cap_table_import*` (the last two hold cap-table and financial data). Downgraded from Critical because the live login page no longer offers "Create account", removing the obvious path to obtaining such a principal. It is **not closed**: commit `19d2b2d` is a client-side gate only, and its own message states that direct API signups remain possible until signup is disabled in Supabase Auth settings, which needs dashboard access.
- Recommended fix: (1) In Supabase → Authentication → Sign In / Up, confirm signup is disabled server-side; until then the client-side gate is bypassable with a single `curl` against the public anon endpoint. (2) Check what `handle_new_user_trigger.sql` does on signup — if it auto-inserts a `team_members` row, the membership predicate protecting the *core* tables is defeated too. (3) Replace every `using (true)` with the `exists (select 1 from team_members where id = auth.uid())` predicate already used elsewhere.

### [M-002] Inline ownership calc bypasses NaN-guard & clamp (recurring, 4th report)
- Severity: **Critical**
- Category: Bug (financial data integrity)
- File: `app/(protected)/companies/[id]/CompanyDetailClient.tsx:92-101` and `:386-399`
- Problem: Both sites hand-roll `calcCombinedOwnershipPct` but omit the per-row `Number.isFinite` guard and the final `clampOwnershipPct([0,100])`. The company detail page can therefore display ownership >100% — inflating `currentValue` and `moic` — and **disagree with the dashboard and analytics for the same company**, which use the clamped library helper. One non-finite `ownership_percentage` from a bad import propagates straight to the displayed figure. Re-verified today: still unchanged since 2026-07-26.
- Recommended fix: Replace both inline reduces with `calcCombinedOwnershipPct(capTable, legalEntities)`. Not auto-fixed: per the auto-fix policy it changes displayed financial figures and requires explicit confirmation. This is a ~6-line change and the highest value-per-effort item open on the platform.

### [M-003] Five pages silently swallow Supabase `.error` and render an empty portfolio (recurring)
- Severity: High
- Category: Bug
- Files: `app/(protected)/dashboard/page.tsx`, `analytics/page.tsx`, `reserves/page.tsx`, `reminders/page.tsx`, `portfolio-kpis/page.tsx`
- Problem: Re-verified today — all five contain **zero** occurrences of the string `error`. Each destructures only `{ data }` and coerces `?? []`. On RLS denial, expired auth, or a connectivity failure the user is shown a fully-rendered, confident **$0 / empty** view rather than an error; Reserves falls through to "No portfolio companies yet.", indistinguishable from a genuinely empty fund. The correct pattern is already established in-repo — `companies/[id]/page.tsx:39-53` inspects `.error` on all 15 parallel queries, maps `PGRST116` to `notFound()`, and throws otherwise, with a comment explaining the reasoning.
- Recommended fix: Port that exact pattern to the five pages. `app/(protected)/error.tsx` already exists, so a thrown error renders correctly with no new UI work. Not auto-fixed: it changes the failure-mode UX of the most-viewed pages.

### [M-004] Sensitive tables still have no RLS migration in the repo (recurring since 2026-07-05)
- Severity: High
- Category: Security
- Source: Supabase — only 3 of the migration files in `supabase/migrations/` contain `ENABLE ROW LEVEL SECURITY`
- Problem: `email_integrations` (Microsoft OAuth **refresh tokens**), `company_kpis`, `safes`, `option_pools`, `share_series`, `waterfall_scenarios`, `pipeline_stages`, `task_saved_filters` are read/written by the app but have no `ENABLE ROW LEVEL SECURITY` or policy anywhere in the repo. Separately, `company_updates` and `reminders` have policies in `rls_tighten_team_members.sql:84,91` with **no accompanying `ENABLE` statement** — a policy on a table without RLS enabled is inert. Because `NEXT_PUBLIC_SUPABASE_ANON_KEY` is public by design, any table where RLS was never enabled by hand in the dashboard is reachable directly through PostgREST, bypassing the app's auth layer entirely. `email_integrations` is the sharpest edge: OAuth refresh tokens are long-lived credentials to the team's mailboxes.
- Recommended fix: Run `SELECT relname, relrowsecurity FROM pg_class WHERE relname IN (...)` against prod to establish ground truth, then commit explicit `ENABLE ROW LEVEL SECURITY` + team-membership policy migrations for every table above so the state is reproducible rather than dashboard-resident.

### [M-005] Server-side "today" is UTC while the client's is now local — cron reminders may fire on the wrong day
- Severity: Medium
- Category: Bug
- File: `app/api/cron/reminders/route.ts:36`
- Problem: The reminder cron computes `const today = new Date().toISOString().split('T')[0]` on Vercel, whose runtime clock is UTC. After F-001/F-002 the client classifies reminders against the Israel-local calendar, so the two now disagree for the first 2–3 hours of each Israeli day: a reminder the UI shows as due today may not yet be picked up by the cron sweep, or vice versa depending on the cron's schedule. This was **not** auto-fixed because unlike the client cases it is not a mechanical swap — `todayLocal()` on a UTC server still returns UTC. It needs a deliberate answer to "which timezone is the fund's business day?" and then an explicit conversion (e.g. `Intl.DateTimeFormat('en-CA', { timeZone: 'Asia/Jerusalem' })`), which is a product decision.
- Recommended fix: Define the fund's business timezone once as a constant (`lib/date-utils.ts` is the natural home), add a `todayInFundTz()` that formats via `Intl` with an explicit `timeZone`, and use it in every server-side route that means "today" — the reminder cron, and check `app/api/cron/lp-report/route.ts` and `send-report/route.ts:56` (whose subject line is date-stamped) for the same assumption. Also worth setting `TZ=Asia/Jerusalem` in the Vercel environment so the two frames converge by default.

## IMPROVEMENT IDEAS

1. **Ban the raw idiom now that the helper exists.** `lib/date-utils.ts` will only prevent recurrence if new code can't reintroduce the old pattern — this bug class has now produced four separate defects across three reports (task trend, sidebar badge, reminder status, date prefills). Add an ESLint `no-restricted-syntax` rule flagging `.toISOString()` followed by `.split('T')[0]` or `.slice(0, 10)`, with a message pointing at `todayLocal()`. This also finally forces the `next lint` configuration that has been missing across every report.

2. **Settle the RLS question with evidence, once.** Five consecutive reports have flagged RLS while noting the migrations were authored without live-DB access, so [M-004] is unfalsifiable from the repo alone. Commit a `scripts/audit-rls.ts` that connects with the service role, dumps `pg_class.relrowsecurity` and `pg_policies` for every table the app touches, and diffs against an expected manifest. Run it in CI. This converts the platform's largest recurring unknown into a pass/fail check.

3. **Make the "error vs. empty" distinction structural.** [M-003] persists because each page hand-rolls its fetch, and `companies/[id]/page.tsx` shows the correct pattern is verbose enough that nobody copies it. A `fetchOrThrow(query)` / `fetchAllOrThrow([...])` helper in `lib/supabase-server.ts` would make the correct path the *shortest* one to write, at which point porting the five pages is close to mechanical.

4. **Give the financial helpers the same treatment the formatters just got.** The test suite jumping 77 → 96 on formatter coverage is exactly why F-001/F-002 were catchable today. [M-002] is the mirror image: `calcCombinedOwnershipPct` is correct and tested, but two call sites bypass it. A test asserting that the company-detail page's ownership figure equals the library helper's output for a fixture with a non-finite and a >100% row would fail today and lock the fix in.

5. **Delete the stale agent worktrees.** `.claude/worktrees/` still holds six-plus abandoned copies of the repo, one with a full `node_modules`. Every repo-wide `grep`/`find` in this audit had to filter them out, and one contains a checked-out copy of the codebase in an unknown state. Prune them and add the path to `.gitignore` and any search-tool ignore config.
