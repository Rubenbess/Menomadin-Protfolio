## FIXED ISSUES

### [F-001] Test runner pulled in tests from `.claude/worktrees/**`
- File: `vitest.config.ts`
- Problem: Vitest's default `exclude` covers `node_modules`, `dist`, and `.next`, but not `.claude/worktrees/**`. Ad-hoc agent worktrees left on disk were being re-discovered, so today's pre-fix run reported "8 test files, 203 tests" when the project actually has 3 files / 60 tests. Yesterday's report's "143/143 passing" was the same contamination — apparent test growth was duplicated worktree counts, not new coverage. Worse, CI was running tests from old worktrees against potentially stale code.
- Fix applied: Added an explicit `exclude` array including `**/.claude/worktrees/**` (and the standard `node_modules`, `dist`, `.next` exclusions to preserve the defaults). Run is now 3 files / 60 tests / 2.0s, down from 8 files / 203 tests / 4.7s. A short docstring above the array explains why this exclusion exists.

### [F-002] `/api/auth/microsoft/status` used service-role unnecessarily
- File: `app/api/auth/microsoft/status/route.ts`
- Problem: Route already authenticated the user via `supabase.auth.getUser()`, then constructed a fresh service-role client to read the calling user's own `email_integrations` row. Service-role bypasses RLS — superfluous when the query is `.eq('user_id', user.id)` on a per-user table.
- Fix applied: Removed the `createClient(...)` import and the service-role client construction. The user-context `supabase` (from `createServerSupabaseClient()`) now performs the read; RLS on `email_integrations` (`user_id = auth.uid()`) is the perimeter. Added a docstring explaining the principle-of-least-privilege rationale so a future contributor doesn't reach for service-role by reflex. Functional behavior unchanged for callers; only the privilege envelope shrinks.

### [F-003] `/api/auth/microsoft/disconnect` used service-role unnecessarily
- File: `app/api/auth/microsoft/disconnect/route.ts`
- Problem: Same pattern as F-002 — session-authenticated route used service-role for a `delete().eq('user_id', user.id)`.
- Fix applied: Switched to the user-context client. RLS enforces ownership; if the session-user check were ever bypassed in the future, RLS would still block cross-user deletes. With service-role, that fallback didn't exist.

### [F-004] `/api/auth/microsoft/callback` used service-role for upsert
- File: `app/api/auth/microsoft/callback/route.ts`
- Problem: Route already validates session-user-matches-state-user before the upsert, then created a separate service-role client to write to `email_integrations`. The user-context client is already in scope (`ssoSupabase` for the auth check); using it for the upsert keeps everything inside the RLS boundary.
- Fix applied: Removed the `createClient` import and the service-role client; reused the existing `ssoSupabase` for the upsert. Comment explains the security perimeter (state-validated user_id + RLS).

### [F-005] DashboardCharts.tsx: hardcoded chart colors invisible in dark mode
- File: `components/DashboardCharts.tsx`
- Problem: `CartesianGrid stroke="#f1f5f9"` (slate-100) and `XAxis/YAxis tick fill="#94a3b8"` (slate-400) are hardcoded — recharts SVG props can't be Tailwind classes. In dark mode the grid is essentially invisible against the dark surface. The `tooltipStyle` const uses `border: '1px solid #f1f5f9'` and an implicit white background that flashes light on dark surfaces. `STATUS_CONFIG` had `bg-emerald-50`/`bg-indigo-50`/`bg-amber-50`/`bg-red-50` with no dark variants; all four status cards rendered as bright pastels in dark mode. The MOIC chart legend used `border-slate-50` and the SectorChart legend text used `text-neutral-700`/`text-neutral-800` without dark variants.
- Fix applied: Imported `useTheme` from `lib/theme-context`. Added two helper factories — `chartColors(isDark)` returning grid/axis/cursor stroke colors, and `tooltipStyleFor(isDark)` returning a fully theme-aware tooltip style (background, border, text color, shadow). Each chart component (`PerformanceChart`, `SectorChart`, `MoicChart`) now reads `theme` and resolves these at render. `STATUS_CONFIG` got `dark:bg-…-900/20` and `dark:text-…-300` variants matching the convention used elsewhere. Legend text and the MOIC chart's bottom border got `dark:text-neutral-400` / `dark:border-neutral-700`. Light-mode rendering is mechanically unchanged.

### [F-008] Verified false-positives flagged by exploration agents
- Files inspected: `lib/calculations.ts`, `app/(protected)/contacts/page.tsx`, `app/api/import/route.ts`
- One agent claimed `calcXIRR` "always returns null after the iterative loop completes." Verified by reading [lib/calculations.ts:113-122](lib/calculations.ts:113) — line 118 returns the converged value via the early `if (Math.abs(next - r) < 1e-8) return next > -1 ? next : null` check inside the loop. Line 122's `return null` is the safety fallthrough hit only when 200 iterations converge no closer than 1e-8, or when the derivative becomes singular. The existing test "computes ~100% IRR for a 2× return in exactly 1 year" passes, confirming convergence-path correctness. No fix needed; agent was misreading control flow.
- Another agent flagged a "CRITICAL N+1 query in `app/(protected)/contacts/page.tsx:30`." Verified — it's a single batched `.in('contact_id', ids)` query, not a loop. O(2) total queries, not O(N+1). No fix needed.
- A third agent flagged `app/api/import/route.ts` as having an "auth bypass" because it uses `supabase.auth.getUser()` without `requireAuth()`. Verified — `getUser()` validates the JWT against Supabase's auth API; the pattern is equivalent. The route correctly returns 401 on no user. With the recent RLS tightening, the user must additionally be in `team_members` for any insert to succeed; RLS is the second perimeter. No fix needed.
