## FIXED ISSUES

### [F-001] Task recurrence form prefilled the wrong next-occurrence date
- File: `components/forms/TaskRecurrenceForm.tsx:34`
- Problem: `next_occurrence` was prefilled with `new Date(Date.now() + 86400000).toISOString().split('T')[0]`. This is the 30th and last instance of the UTC-serialisation idiom that produced F-001/F-002/F-003 yesterday — the sweep converted six date-input prefills but missed this one because it computes tomorrow via millisecond arithmetic rather than the `new Date()` shape the earlier search matched. Between local midnight and 02:00/03:00 Israel time it prefills **today** instead of tomorrow, so a recurrence rule created in that window fires a day early on its first occurrence and every occurrence thereafter inherits the shifted anchor. Recurring tasks are the mechanism behind scheduled portfolio reviews and reporting deadlines, so a persistent one-day drift is not cosmetic.
- Fix applied: Replaced with `addDaysLocal(1)` from `lib/date-utils.ts`, matching the pattern established for the other six prefills. Import added. Covered by the existing `addDaysLocal` cases in `__tests__/date-utils.test.ts`; 105/105 still pass and `tsc` is clean.

## MANUAL ACTION REQUIRED

### [M-001] Excel import inflates sub-1% ownership stakes by 100× (NEW)
- Severity: **Critical**
- Category: Bug (financial data integrity)
- File: `app/api/import/route.ts:30-34`, consumed at `:223` and written at `:280`
- Problem: `pct()` guesses whether a value is a fraction or a percentage with `n < 1 ? n * 100 : n`. The column it parses is named **"Ownership Percentage"** (`:223`), so a cell containing `0.5` means half a percent — the heuristic multiplies it to `50`, a **100× overstatement**. The result is written straight to `cap_table.ownership_percentage` (`:280`), which is the input to `getFundOwnershipPct`, `calcCombinedOwnershipPct`, `calcCurrentValue`, and `calcMOIC`. A single small stake therefore inflates that company's displayed valuation and MOIC by two orders of magnitude, and does so on the dashboard, analytics, reserves, and company detail pages simultaneously because they all read the same corrupted row. Small stakes are exactly what a fund holds after dilution across several rounds, so this is not a rare edge case. Critically, this bug **persists in the database** — it is not a rendering error that a front-end fix clears.
- Recommended fix: Do not auto-fix — the fraction-vs-percent ambiguity is genuinely undecidable for a value like `0.5` without knowing the source spreadsheet's convention, so the correct resolution is a product decision. Concretely: (1) decide the convention for the "Ownership Percentage" column and honour it literally, removing the heuristic; (2) if a heuristic must remain, restrict it to values where the fraction reading is unambiguous (`n < 0.01`, i.e. below 1% expressed as a percentage is implausible for a cap-table row) and log every coercion; (3) **audit existing data** — `SELECT company_id, shareholder_name, ownership_percentage FROM cap_table WHERE ownership_percentage BETWEEN 10 AND 100` and reconcile against source spreadsheets, since already-imported rows are silently wrong; (4) add a unit test asserting `pct(0.5) === 0.5`, which fails today.

Not auto-fixed: per the auto-fix policy it changes displayed financial figures and requires explicit confirmation. This remains a ~6-line change and the highest value-per-effort item open on the platform.

### [M-004] `USING (true)` RLS policies grant any authenticated principal full access (recurring)
- Severity: High
- Category: Security
- Source: `supabase/migrations/tasks_system.sql:143-189`, `notifications.sql:24`, `legal_entities.sql:12-13`, `deal_report_recipients.sql:12,16,20`, `add_cap_table_import.sql:60,68,76`
- Problem: These policies are `for all to authenticated using (true) with check (true)` — no `team_members` membership check, unlike the core tables hardened by `rls_tighten_team_members.sql`. Any authenticated principal gets full read/write on `tasks` and all nine task tables, `notifications`, `legal_entities`, `deal_report_recipients`, and `cap_table_import*` (the last two hold cap-table and financial data). Held at High rather than Critical because the live login page no longer offers "Create account". It is **not closed**: `19d2b2d` is a client-side gate only, and its own commit message states direct API signups remain possible until signup is disabled in Supabase Auth settings, which needs dashboard access this run cannot reach.
- Recommended fix: (1) In Supabase → Authentication → Sign In / Up, confirm signup is disabled server-side; until then the client-side gate is bypassable with a single `curl` against the public anon endpoint. (2) Check what `handle_new_user_trigger.sql` does on signup — if it auto-inserts a `team_members` row, the membership predicate protecting the *core* tables is defeated too. (3) Replace every `using (true)` with the `exists (select 1 from team_members where id = auth.uid())` predicate already used elsewhere.

### [M-005] Sensitive tables still have no RLS migration in the repo (recurring since 2026-07-05)
- Severity: High
- Category: Security
- Source: Supabase — only 3 migration files in `supabase/migrations/` contain `ENABLE ROW LEVEL SECURITY`
- Problem: `email_integrations` (Microsoft OAuth **refresh tokens**), `company_kpis`, `safes`, `option_pools`, `share_series`, `waterfall_scenarios`, `pipeline_stages`, `task_saved_filters` are read/written by the app but have no `ENABLE ROW LEVEL SECURITY` or policy anywhere in the repo. Separately, `company_updates` and `reminders` have policies in `rls_tighten_team_members.sql:84,91` with **no accompanying `ENABLE` statement** — a policy on a table without RLS enabled is inert. Because `NEXT_PUBLIC_SUPABASE_ANON_KEY` is public by design, any table where RLS was never enabled by hand in the dashboard is reachable directly through PostgREST, bypassing the app's auth layer entirely. `email_integrations` is the sharpest edge: OAuth refresh tokens are long-lived credentials to the team's mailboxes.
- Recommended fix: Run `SELECT relname, relrowsecurity FROM pg_class WHERE relname IN (...)` against prod to establish ground truth, then commit explicit `ENABLE ROW LEVEL SECURITY` + team-membership policy migrations for every table above so the state is reproducible rather than dashboard-resident.

### [M-006] Server-side "today" is UTC while the client's is now local (recurring)
- Severity: Medium
- Category: Bug
- Files: `app/api/cron/reminders/route.ts:36`, `app/api/send-report/route.ts:56`, `app/api/import/route.ts:9,15`
- Problem: The reminder cron computes `new Date().toISOString().split('T')[0]` on Vercel, whose runtime clock is UTC. After the F-001/F-002 client fixes the UI classifies reminders against the Israel-local calendar, so the two frames disagree for the first 2–3 hours of each Israeli day. `send-report/route.ts:56` date-stamps the email subject from the same UTC frame. `import/route.ts:9,15` is the sharper case newly noted today: when a spreadsheet row has no parseable date, `toDate()` **silently stamps it with the UTC "today"** — so an investment or cap-table row imported in the early-morning window is dated yesterday, and there is no warning that a date was substituted at all.
- Recommended fix: Define the fund's business timezone once as a constant in `lib/date-utils.ts`, add `todayInFundTz()` formatting via `Intl.DateTimeFormat('en-CA', { timeZone: ... })`, and use it in every server route that means "today". Separately, `toDate()` should not silently invent a date for financial rows — surface unparseable dates as an import warning instead. Also worth setting `TZ=Asia/Jerusalem` in the Vercel environment so the two frames converge by default.

## IMPROVEMENT IDEAS

1. **Test the import path the way the formatters got tested.** [M-001] is a two-line function with an obviously wrong branch that has been shipping corrupt financial data, and no test would have caught it because `app/api/import/route.ts` has none. Its pure helpers — `pct`, `num`, `toDate`, `mapInstrument`, `mapStrategy` — are trivially testable in isolation. A dozen cases here covers the platform's single highest-risk surface: the only code path that *writes* financial figures in bulk.

2. **Ban the raw date idiom now that the sweep is complete.** F-001 today was the 30th and final instance, found only because it was checked by hand. This bug class has produced five defects across three reports. Add an ESLint `no-restricted-syntax` rule flagging `.toISOString()` followed by `.split('T')[0]` or `.slice(0, 10)` outside `lib/csv-export.ts` / `lib/pdf-export.ts` filename stamps, with a message pointing at `todayLocal()`. This also finally forces the `next lint` configuration missing from every report.

3. **Settle the RLS question with evidence, once.** Six consecutive reports have flagged RLS while noting the migrations were authored without live-DB access, so [M-005] is unfalsifiable from the repo alone. Commit a `scripts/audit-rls.ts` that connects with the service role, dumps `pg_class.relrowsecurity` and `pg_policies` for every table the app touches, and diffs against an expected manifest. Run it in CI. Today's API-auth audit came back clean precisely because it was mechanically checkable — RLS deserves the same treatment.

4. **Add a data-integrity reconciliation query.** [M-001] means wrong numbers are already at rest, and nothing on the platform would reveal that. A `scripts/check-invariants.sql` asserting the things that must hold — per-company `SUM(ownership_percentage) <= 100`, no non-finite or negative amounts, no cap-table row without a matching company — turns silent corruption into a failing check, and would flag both [M-001]'s and [M-002]'s symptoms.

5. **Make the "error vs. empty" distinction structural.** [M-003] persists across four reports because each page hand-rolls its fetch and the correct pattern in `companies/[id]/page.tsx` is verbose enough that nobody copies it. A `fetchOrThrow(query)` / `fetchAllOrThrow([...])` helper in `lib/supabase-server.ts` would make the correct path the *shortest* one to write, at which point porting the five pages is close to mechanical.
