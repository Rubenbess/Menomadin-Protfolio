### [F-001] `getTask` read had no authentication guard
- File: `actions/tasks.ts:99` (`getTask`)
- Problem: Read a full task (incl. assignees, company context, recurrence rule) by id with no `getUser()` check, while every sibling in the file (created/updated this cycle) is guarded. Sole reliance on RLS is an inconsistent posture on a financial platform; this was the last unguarded read in `actions/tasks.ts`.
- Fix applied: Added `const { data: { user } } = await supabase.auth.getUser(); if (!user) return { error: 'Not authenticated', data: null }` before the query, returning the existing `{ error, data }` shape.

### [F-002] Kanban drag/delete never reverted on a failed write (silent DB divergence)
- File: `app/(protected)/tasks/TasksBoard.tsx` — `handleDragEnd` (~line 240) and `handleDeleteTask` (~line 252)
- Problem: Both applied an optimistic `setLocalTasks` then `await updateTask/deleteTask` with **no `result.error` check**. On a failed write the card had already moved / disappeared, the user believed it persisted, and local state silently diverged from the DB until a manual refresh. (Prior M-015.)
- Fix applied: Snapshot `localTasks` before the optimistic update; on `result?.error`, restore the snapshot and return (no `router.refresh()`). This mirrors the codebase's own canonical pattern in `RemindersClient` exactly (silent revert + resync), so it introduces no new dependency or UX convention.

### [M-001] `team_members` RLS-hardening migration is still UNTRACKED in git
- Severity: **Critical** · Category: Security
- Source: `supabase/migrations/20260618_secure_team_members.sql` (shows `??` in `git status`)
- Problem: This is the only file that enables RLS on `team_members`, installs the anti-self-escalation guard trigger (`trg_enforce_team_member_role`), defaults new signups to `viewer`, and adds a `menomadin.com` email-domain allowlist. `team_members.role` is the authority behind `requireAdminAuth` and every membership RLS policy. If it is neither committed nor confirmed live, an authenticated browser client could `update team_members set role='admin' where id=<self>` and seize full control of all portfolio/cap-table/investment data. The migration itself is well-written and self-documents its verification steps — it simply needs to be committed and applied.
- Recommended fix: `git add` + commit the migration. Verify live: `select relrowsecurity from pg_class where relname='team_members'` must be `t`, and `trg_enforce_team_member_role` must exist. Disable open signups in Supabase Auth as defense-in-depth.

### [M-002] `safes` table has NO RLS in any tracked migration
- Severity: **Critical** · Category: Security
- Source: `supabase/migrations/safes_external_investors.sql:4` only runs `alter table safes add column…`; no `enable row level security`/policy for `safes` exists anywhere; `convert_safe_rpc.sql` has no `revoke execute … from anon, public`.
- Problem: `safes` holds SAFE instruments (investor, valuation cap, conversion terms) — core deal financials. Postgres defaults RLS off, so unless enabled out-of-repo the table is readable/writable by anyone holding the public `anon` key shipped to every browser.
- Recommended fix: Verify `select relrowsecurity from pg_class where relname='safes'`; if false, `ALTER TABLE safes ENABLE ROW LEVEL SECURITY` + a team-member membership policy mirroring the core tables. Consider revoking `convert_safe` from `anon, public`.

### [M-003] DPI is hardcoded to zero on dashboard, analytics, and the LP report
- Severity: **Critical** · Category: Bug (Financial calculation)
- File: `app/(protected)/dashboard/page.tsx:124` and `app/(protected)/analytics/page.tsx:82` — `const dpi = calcDPI(0, …)`
- Problem: The distributions argument is the literal `0`, so DPI always renders `0.00x`. It is shown to LPs as a real metric, not a "no data yet" state. UNCHANGED across multiple checks.
- Recommended fix: Aggregate real distribution/realized-exit data into `calcDPI`. If no distributions data model exists yet, **hide** the metric rather than display a false `0.00x`. (Shares a root cause with M-004/M-008 — see Improvement Idea #2.)

### [M-004] Written-off / exited companies are still valued at last-round mark → IRR & MOIC overstated
- Severity: **Critical** · Category: Bug (Financial calculation)
- File: `app/(protected)/dashboard/page.tsx:101` (and parallel logic in `analytics/page.tsx:55-66`) — `currentValue = latestRound ? calcCurrentValue(ownershipPct, latestRound.post_money) : 0`, no `status` check.
- Problem: A `written-off` company still contributes positive terminal value to portfolio MOIC/TVPI and to the synthetic XIRR inflow, inflating reported returns. Exited companies should reflect realized proceeds, not the last private mark. UNCHANGED.
- Recommended fix: Zero `currentValue` for `status === 'written-off'`; for `status === 'exited'`, use realized proceeds. Confirm where realized proceeds are stored before implementing.

### [M-005] `calcCurrentValue` still has no finiteness guard on `latestPostMoney`
- Severity: **Critical** · Category: Bug (Financial calculation)
- File: `lib/calculations.ts:32-34` — `return (ownershipPct / 100) * latestPostMoney`
- Problem: The ownership-% side is now protected (`calcCombinedOwnershipPct`/`clampOwnershipPct` clamp and NaN-guard it), but the `latestPostMoney` argument (`latestRound.post_money`) is still unguarded. A legacy/`null`/`NaN` `post_money` (the validation guard in `rounds.ts` only applies to new writes) makes `currentValue` `NaN`, which propagates through `calcMOIC` (numerator unguarded), `totalCurrentValue` (`reduce` → NaN), TVPI, and the portfolio XIRR terminal inflow — silently corrupting every top-line number. `fmtMultiple`/`fmtPct` (calculations.ts:563-569) then render literal `"NaNx"`/`"NaN%"`.
- Recommended fix: `if (!Number.isFinite(ownershipPct) || !Number.isFinite(latestPostMoney)) return 0`. Mirror finiteness checks in `calcMOIC`/`calcTVPI` numerators and have `fmtMultiple`/`fmtPct` render a placeholder (e.g. `"—"`) on non-finite input. **Pure defensive guard, no behavior change on valid input — safe to approve quickly.** Flagged (not auto-applied) only because Phase-3 rules require confirmation before editing financial-calc code.

### [M-006] Waterfall drops cap-excess proceeds when there is no uncapped common
- Severity: **Critical** · Category: Bug (Financial calculation)
- File: `lib/calculations.ts:500-512` (`calcWaterfall`)
- Problem: When participation caps trigger, `capExcess` is redistributed only to uncapped common (lines 501-512). If `uncappedEquiv === 0` (all-participating-capped stack, or zero common shares), the `if` is skipped and `capExcess` is silently dropped — yet the function still returns `{ totalProceeds: exitValue }` (line 535), so `WaterfallScenarioPanel` renders proceeds bars that don't sum to the exit value (money disappears). The only sum-to-exit test uses a single common holder, so this path is untested. UNCHANGED.
- Recommended fix: When no uncapped common exists, redistribute `capExcess` pro-rata to remaining uncapped participants; if everyone is capped, fall back to pro-rata by issued shares so `sum(proceeds) === exitValue`. Add an invariant test asserting `sum(proceeds) ≈ exitValue` (see Improvement Idea #1). Multi-tranche conversion/cap iteration (prior M-007) and discount-only-SAFE inclusion (prior M-009, share-basis half now fixed) remain related open items — confirm intended semantics with the business.

## IMPROVEMENT IDEAS
1. **Add a `sum(proceeds) === exitValue` invariant test to the waterfall, plus multi-tier seniority / participation-cap cases.** The waterfall ([M-006]) is the most financially consequential and least-tested surface — a property-style invariant would have caught the cap-excess drop immediately. The XIRR rewrite this cycle shows the testing appetite is there; extend it to the waterfall.
2. **Build a realized-distributions data model and wire it through DPI + IRR + exited/written-off marks ([M-003]/[M-004]/[M-007]).** All three share one root cause: the platform tracks invested capital and current marks but has no realized cash-flow concept, so DPI is faked as `0` and dead companies inflate returns. This is the single highest-leverage data-model investment for LP-facing accuracy.
3. **Commit the working tree now, in logical units, and apply + verify the RLS migration ([M-009]/[M-001]).** A substantial, correct improvement batch and the critical security migration currently exist only on one workstation. Committing also lets review/CI finally see them.
4. **Adopt a `loadGuarded()` server-page wrapper that throws on `.error`.** The new `error.tsx` boundary is in place but inert until pages throw ([M-008]). A one-line wrapper would make the safe path the default across all six financial pages and let the boundary do its job.
5. **Configure ESLint for real and gate the build on it.** `next lint` is still a no-op in scheduled/CI runs. Flat-config ESLint with `no-floating-promises`, `react-hooks/exhaustive-deps`, and `no-explicit-any` would have caught the optimistic-mutation ([F-002]) and stale-closure classes automatically — turning recurring manual findings into compile-time failures.
