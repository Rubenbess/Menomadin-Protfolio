## FIXED ISSUES

### [F-001] `deleteTeamMember` allowed an admin to delete their own account → zero-admin org
- File: `actions/team-members.ts:58-78`
- Problem: Carryover M-038. The sibling `updateTeamMember` already strips the `role` field on self-update (`actions/team-members.ts:47-50`) precisely to prevent an admin from demoting themselves into a zero-admin state. The delete path lacked the same instinct: `deleteTeamMember(self.id)` would happily succeed, and on a single-admin Menomadin org would brick every subsequent admin-gated action (team-member create/update/delete, task-automation owner mutations, future admin-only writes). RLS does not catch this because RLS evaluates the row, not the principal.
- Fix applied: Added `if (id === user.id) return { error: 'You cannot delete your own account.' }` immediately after the admin-role check at `actions/team-members.ts:71-73`. Mirrors the self-protection pattern already proven on the update path. Three-line defensive addition, no logic change to the existing happy path, no schema/migration impact. `npx tsc --noEmit` exit 0.

## MANUAL ACTION REQUIRED

### [M-042] `convert_safe` RPC has no idempotency check — calling twice will double-insert cap_table rows (**Critical**, NET-NEW)
- Severity: **Critical** (financial-data integrity)
- Category: Bug / Data Integrity
- File or Source: `supabase/migrations/convert_safe_rpc.sql:19-33`, called from `actions/safes.ts:94`
- Problem: New finding from today's audit after the migration finally got tracked. The RPC unconditionally `update safes set status = 'converted', converted_round_id = $1, …` then unconditionally `insert into cap_table (...)`. **There is no check that the SAFE was previously unconverted.** If `convertSafe()` is invoked twice on the same `safeId` (network retry, double-click in the UI, server action re-triggered after a page navigation, an admin re-running a back-fill), the second call: (1) succeeds in the update step (status is already 'converted', `returning company_id` still finds the row); (2) successfully inserts a **second** `cap_table` row for the same holder + same round. The result is a duplicate ownership row that double-counts the holder's shares in every subsequent waterfall, MOIC, and ownership-summation calculation. The TS-layer wrapper at `actions/safes.ts:57-106` also has no `safe.status` guard before invoking the RPC. The RPC was *intended* to make conversion atomic, and it succeeds at that — but in eliminating the TS-layer rollback, it also removed the implicit "check status before doing anything" the audit recommended on 2026-05-20.
- Recommended fix: Two layers, defence-in-depth:
  1. **RPC**: change the update to `update safes set ... where id = p_safe_id and status = 'unconverted'`. If no row is returned, `raise exception 'SAFE % already converted or not found', p_safe_id` instead of the current "not found" message. This makes double-conversion atomically impossible at the DB layer.
  2. **TS caller** (`actions/safes.ts:66-69`): after fetching the SAFE, add `if (safe.status === 'converted') return { error: 'This SAFE has already been converted.' }`. This produces a friendlier UI error than letting the RPC raise.
  3. **Backfill check**: run `select safe_id, count(*) from cap_table where safe_id is not null group by safe_id having count(*) > 1;` (or equivalent join) in production Supabase to catch any duplicates that may have been created in the brief window since `ae4a56f` deployed.

### [M-034] `/api/extract` has no bound on remote-file size (carryover, Medium, day 3)
- Severity: Medium
- Category: Security / Performance
- File or Source: `app/api/extract/route.ts:44-45, 60-61, 79-80, 103-104, 124`
- Problem: Yesterday's `6ee88be` commit added media-type validation against an allowlist and pinned the model version — good. But every branch (`isPdf`, `isImage`, `isExcel`, fallback text) still unconditionally calls `fileRes.arrayBuffer()` or `fileRes.text()` with no Content-Length check, no streaming, no size cap. An authenticated caller pointing `file_url` at a multi-GB file on the allowed storage host buffers the whole payload into Vercel function memory before dispatch to Anthropic, OOM'ing the lambda.
- Recommended fix: After `fileRes.ok`, parse `fileRes.headers.get('content-length')` and reject `> 25 * 1024 * 1024` (or whatever Anthropic's PDF/image limits are). For unknown-length responses, switch to streaming read with an in-flight byte counter. A 5-line helper `assertBoundedFile(res, maxBytes)` shared across all branches keeps it DRY.

### [M-043] `lib/rate-limit.ts` `Map<string, Window>` grows unbounded — leak under high token cardinality (NET-NEW, Low)
- Severity: Low (Vercel cold-instance recycling masks this in practice)
- Category: Bug / Performance
- File or Source: `lib/rate-limit.ts:17, 27-30`
- Problem: New finding from today's review of the rate limiter introduced in `8e2a073`. The module-level `Map<string, Window>` adds an entry on first request for a key (e.g. `founder-update:<token>`) and only replaces it when a new request arrives for the same key after `resetAt`. If no follow-up request arrives, the entry sits in the map forever. For founder-update tokens this means **one entry per unique token ever submitted from**; on a long-lived process this is a slow memory leak. The module docs already acknowledge "Vercel's serverless model means each cold instance has its own counter," so on Vercel the leak is bounded by instance lifetime — but if this code ever runs under a long-lived Node process (custom server, self-hosted, future migration to Upstash/KV), the leak materialises. The fix is trivial.
- Recommended fix: Add a lazy sweep at the top of `checkRateLimit`: `if (windows.size > 1000) { for (const [k, w] of windows) if (w.resetAt <= now) windows.delete(k); }`. Or set a `setInterval` cleanup if module-init side effects are acceptable. Or — simplest — when migrating to Upstash/KV (as the module docstring already plans), the leak goes away by construction. Flag as Low because the practical exposure is currently zero.
