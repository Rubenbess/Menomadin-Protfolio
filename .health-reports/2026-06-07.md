## FIXED ISSUES

### [F-001] cap_table writes had no auth gate and no bounds on ownership %
- File: `actions/cap-table.ts`
- Problem: `createCapTableEntry` / `deleteCapTableEntry` relied entirely on RLS — no `getUser()` gate — and accepted any `ownership_percentage` (NaN, Infinity, negative, or >100). This column feeds the LP-report Ownership column and every downstream FMV/MOIC computation; a bad value corrupts fund-level math silently.
- Fix applied: Added `getUser()` gate to both functions; reject `ownership_percentage` that is non-finite, negative, or >100 via `isInvalidMetric(...) || > 100` before insert.

### [F-002] company_kpis writes had no auth gate, no numeric validation, no note clamp
- File: `actions/kpis.ts`
- Problem: `createKPI` inserted unvalidated `revenue/arr/run_rate/burn_rate/cash_runway/headcount/gross_margin` (NaN/Infinity/negative) and an unbounded `notes` field, with no `getUser()` gate. These cascade into KPI/revenue charts and valuation math.
- Fix applied: Added `getUser()` gate; validate every numeric field with `isInvalidMetric` (allowing negative for `burn_rate` only); `clampText(notes)`. `deleteKPI` also gated.

### [F-003] reserves writes had no auth gate or validation
- File: `actions/reserves.ts`
- Problem: `upsertReserve` / `deleteReserve` were RLS-only; `reserved_amount` / `deployed_amount` unvalidated; `notes` unbounded. Reserve figures drive follow-on capital planning.
- Fix applied: `getUser()` gate on both; `isInvalidMetric` on both amounts; `clampText(notes)`.

### [F-004] waterfall_scenarios writes had no auth gate; exit_value unvalidated
- File: `actions/waterfall-scenarios.ts`
- Problem: `createWaterfallScenario` accepted any `exit_value` (the driver of the entire liquidation waterfall) and was RLS-only. A non-finite/negative exit value corrupts every holder's modeled proceeds.
- Fix applied: `getUser()` gate on create + delete; `isInvalidMetric(exit_value)`; `clampText(name)`.

### [F-005] saveDocument allowed registering an arbitrary external file_url (SSRF vector)
- File: `actions/documents.ts`
- Problem: `saveDocument` had no auth gate and no URL allowlist, unlike the hardened `/api/documents` route. A registered `file_url` is later fetched server-side by `/api/extract` — an attacker-controlled URL could drive SSRF or LLM-credit drain. (Currently no in-tree caller, but the export is reachable as a server action.)
- Fix applied: `getUser()` gate; require `isAllowedFileUrl(file_url)` (existing `lib/url-allowlist.ts` helper restricting to the Supabase storage host). `deleteDocument` also gated.

### [F-006] contacts (PII) mutators had no auth gate — prior-audit regression
- File: `actions/contacts.ts`
- Problem: Despite a prior report claiming contacts was hardened, **no contact mutator had a `getUser()` gate** (only try/catch + date validation had been added). Contact PII (name/email/phone/address/notes) was created/updated/deleted under RLS alone; `notes` unbounded.
- Fix applied: Added `getUser()` gate to all seven mutators (`createContact`, `updateContact`, `deleteContact`, `createInteraction`, `deleteInteraction`, `linkContactToCompany`, `unlinkContactFromCompany`) and `clampText(notes)` on create/update.

### [F-007] companies mutators (incl. destructive contact wipe) had no auth gate
- File: `actions/companies.ts`
- Problem: `createCompany` / `updateCompany` / `deleteCompany` / `upsertContacts` were RLS-only. `upsertContacts` does a destructive delete-all-then-reinsert of a company's contacts — running this without an explicit auth gate is the highest-blast-radius of the group.
- Fix applied: `getUser()` gate added to all four. (Note: `logo_url` is still not allowlist-validated — see M-007 family; left as a flagged item, not changed here.)

### [F-008] WaterfallScenarioPanel mutated memoized data during render
- File: `components/WaterfallScenarioPanel.tsx:203,315`
- Problem: `result.holders.sort(...)` / `savedResult.holders.sort(...)` sort **in place**, mutating arrays held inside a `useMemo` on every render — fragile and a React anti-pattern (mutating values React assumes are stable).
- Fix applied: Copy before sorting — `[...result.holders].sort(...)` and `[...savedResult.holders].sort(...)`. No behavioural change.

## MANUAL ACTION REQUIRED

### [M-001] SAFE "Est. Ownership" headline metric can render an impossible >100%
- Severity: **Critical**
- Category: Bug (financial)
- File: `app/(protected)/companies/[id]/CompanyDetailClient.tsx:217-220`
- Problem: The KPI sums `calcSafeEstimatedOwnership(...)` across all unconverted SAFEs. Each call is capped at 100% individually (`lib/calculations.ts:218`), but the **sum is uncapped** — two SAFEs each estimating 60% render "120.00%", a financially impossible ownership figure shown as a headline metric. `calcSafeEstimatedOwnership`'s own docstring states each value is a per-SAFE upper bound, not additive.
- Recommended fix: Not auto-fixed (touches financial display semantics — Phase 3 rule 4). Either cap the aggregate `Math.min(100, sum)`, or relabel as a non-additive upper-bound range / render per-SAFE. Confirm with finance whether summing pre-dilution estimates is meaningful at all.

### [M-002] Portfolio MOIC is defined as identical to TVPI
- Severity: High
- Category: Bug (financial semantics)
- File: `app/(protected)/analytics/AnalyticsClient.tsx:35-36`
- Problem: `tvpi = currentValue / totalInvested; moic = tvpi`. MOIC and TVPI are distinct metrics; there is no distributions/realized term, so both headline figures are the same number under two different labels. Guarded against NaN, so not a crash — but a potential misstatement on a finance dashboard.
- Recommended fix: Route through `calcTVPI`/`calcMOIC` (`lib/calculations.ts`) and incorporate realized distributions where available; if the simplification is intentional (no portfolio-level distributions tracked here), drop the separate "MOIC" label or annotate it.

### [M-003] Two conflicting RLS migrations define incompatible policies on 7 core tables
- Severity: High
- Category: Security
- Source: `supabase/migrations/table_permissions.sql:83-236` vs `supabase/migrations/rls_tighten_team_members.sql:20-66`
- Problem: Both migrations `DROP POLICY authenticated_all` and then create *different* policy sets (RBAC `can_perform_action()` vs `team_members_all`) on `companies/rounds/investments/cap_table/reserves/documents/pipeline`, without either dropping the other's policies. Effective enforcement depends on apply order and is ambiguous.
- Recommended fix: Choose one model; in the surviving migration explicitly `DROP POLICY IF EXISTS` the other's named policies before creating. Verify live policy set in Supabase.

### [M-004] cap_table_imports / cap_table_import_data are world-readable/writable to any authed user
- Severity: High
- Category: Security
- Source: `supabase/migrations/add_cap_table_import.sql:58-77`
- Problem: Policies use `USING (TRUE)` / `WITH CHECK (TRUE)`. These tables hold imported cap-table (ownership) data — any authenticated user can read/insert/update all rows regardless of company.
- Recommended fix: Scope to `exists (select 1 from team_members where id = auth.uid())` (or join the parent company's permission), matching the hardening migration.

### [M-005] Several app-queried tables have no versioned CREATE TABLE / RLS (incl. OAuth token store)

- Category: Security
- Source: Supabase — `company_kpis`, `safes`, `share_series`, `option_pools`, `waterfall_scenarios`, `email_integrations`

Their RLS state is unverifiable from source.

## IMPROVEMENT IDEAS
1. **Lint rule against ungated server actions.** This run (and the last several) keep finding `actions/*.ts` mutators that skip the `getUser()` gate. A small custom ESLint rule (or a test that greps every `export async function` in `actions/` for an `auth.getUser()` call) would make the whole class of M-007..M-013 impossible to reintroduce.
2. **Bring the RLS model fully into version control.** M-003/M-004/M-005 all stem from the database's true policy state not being reconstructable from the repo. Reconcile the two competing migrations, add migrations for the six ad-hoc tables, and add a CI check that fails if `schema.sql`/migrations reference a table the app queries but never `ENABLE ROW LEVEL SECURITY` on it.
3. **Centralize financial display through lib/calculations.ts and add property tests.** M-001 (SAFE sum >100%) and M-002 (MOIC≡TVPI) are both inline-math drift. Move every rendered financial figure behind the lib utilities and add fast-check/property tests asserting invariants (ownership ∈ [0,100], MOIC ≥ 0, no NaN/Infinity reaches a formatter).
4. **A canonical async-fetch hook.** M-015's stale-response race exists in two components and will recur. Extract a `useAsyncData(key, fetcher)` hook with built-in cancellation/loading-reset and migrate the panels to it.
5. **Resolve the standing env-var gap (M-006) and add a startup config check.** `REPORT_API_KEY` has been missing in prod for ~18 days, silently 503-ing report sends. A boot-time assertion (or a `/api/health` route listing which required env vars are present) would surface this on the next deploy instead of in an audit.
