## MANUAL ACTION REQUIRED

### [M-001] `calcWaterfall` silently loses exit proceeds — distribution does not sum to the exit value
- Severity: **Critical**
- Category: Bug (financial data integrity)
- File or Source: `lib/calculations.ts:486-605` (Step 3, lines 538-587), surfaced in `components/WaterfallScenarioPanel.tsx:168-260`
- Problem: the residual distribution in Step 3 has two paths on which money simply disappears, while the function still reports `totalProceeds: exitValue`.

  **Leak A — capped participation excess with no uncapped common (lines 570-581).** When a participating preferred holder hits its participation cap, the excess is collected into `capExcess` and redistributed only to `uncappedCommon`, filtered as `!h.isPreferred && !cappedIds.has(h.id)`. If that set is empty — or its `uncappedEquiv` is 0 — the `if (uncappedEquiv > 0)` guard fails and `capExcess` is dropped on the floor. Converting preferred are excluded from the redistribution target set as well, even though they participate in the residual pro-rata in every other respect, so they cannot absorb it either.

  Reproduced: two 2x-capped participating preferred, $1M invested each, 1,000 shares each, no common, exit **$10,000,000** → holder proceeds sum to **$4,000,000**. **$6,000,000 (60% of the exit) is unallocated.**

  **Leak B — residual with no participants (line 546).** If `totalParticipatingEquiv` is 0 (every holder is non-converting preferred, e.g. a holder carrying invested capital but zero recorded shares), `remaining` is never distributed. Reproduced: one preferred holder, $1M invested, 0 shares, exit **$5,000,000** → proceeds sum to **$1,000,000**, **$4,000,000 lost.**

  Why this matters here specifically: `WaterfallScenarioPanel` renders `fmt$$(result.totalProceeds)` as the column total in the footer (line 260) and computes every row's share as `h.proceeds / result.totalProceeds` (lines 175, 224, 232, 323). Because `totalProceeds` is the *input* exit value rather than the sum of what was actually allocated, the UI presents a table whose rows visibly do not add up to its own stated total, and whose "% of exit" column sums to less than 100%. There is no assertion, warning, or console message anywhere on this path — `calcWaterfall` even returns a hardcoded `warnings: []` (line 604) despite `WaterfallResult` carrying a warnings channel that `buildWaterfallHolders` populates and the panel already renders (line 151). An LP or IC reading a saved scenario has no signal that the numbers are incomplete.

  Severity is Critical under the standing rule that financial calculation bugs are always Critical, and independently because the failure is silent and the output is externally distributed.
- Recommended fix:
  1. Add a conservation invariant at the end of `calcWaterfall`: compute `allocated` as the sum of `payouts.values()` and, when `Math.abs(allocated - exitValue) > 0.01`, push an explicit warning into the returned `warnings` array rather than returning `[]`. Have `WaterfallScenarioPanel` render `result.warnings` alongside the existing `holderWarnings` block at line 151. This makes any future leak loud instead of silent, and is worth doing regardless of how the allocation itself is corrected.
  2. Fix Leak A by widening the cap-excess redistribution target to all uncapped residual participants — uncapped common **and** converting preferred — and by looping the redistribution until either no excess remains or no uncapped participant is left, since a single redistribution pass can itself push another holder over its cap.
  3. Fix Leak B by deciding explicitly what happens to residual value when no one participates. The two defensible answers are to distribute pro-rata by invested capital among the preferred, or to treat zero-share preferred as a data-entry error and reject it upstream in `actions/share-series.ts`. Either is acceptable; silently keeping the money is not.
  4. Add the property-based tests proposed in the previous run's improvement idea 2 — assert that holder proceeds sum to the exit value across randomized cap tables. Both leaks above are caught immediately by that single invariant, and the current suite does not test conservation at all (`__tests__/calculations.test.ts:488-524` covers only three waterfall cases, none with participation caps).
- Not auto-fixed: Phase 3 rule 4 forbids this agent from changing financial calculation logic. Step 3 above is also a genuine modelling decision, not a mechanical correction.

### [M-002] `roles` and `table_permissions` tables have RLS disabled — privilege escalation
- Severity: **Critical**
- Category: Security
- File or Source: `supabase/migrations/table_permissions.sql` (Supabase schema)
- Problem: **unchanged since 2026-09-15 and still open — verified again today.** Only 4 migration files contain `ENABLE ROW LEVEL SECURITY`, and neither `roles` nor `table_permissions` appears in any `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` statement anywhere in the repo. These are the two tables that *define* the RBAC matrix that every other policy delegates to via `can_perform_action()`. With no `GRANT`/`REVOKE` overrides present, Supabase's default grants to `authenticated` apply, so a `viewer`-role user can run `update table_permissions set can_delete = true where role_name = 'viewer'` from the browser with the public anon key and gain delete rights over the entire investment and cap-table dataset.
- Recommended fix: unchanged from the 2026-09-15 report —
  ```sql
  ALTER TABLE roles ENABLE ROW LEVEL SECURITY;
  ALTER TABLE table_permissions ENABLE ROW LEVEL SECURITY;
  CREATE POLICY "roles_read" ON roles FOR SELECT TO authenticated USING (true);
  CREATE POLICY "table_permissions_read" ON table_permissions FOR SELECT TO authenticated USING (true);
  -- No INSERT/UPDATE/DELETE policy: permission changes go through a
  -- service-role admin path only.
  ```
  This is now the third consecutive run reporting an unmitigated privilege-escalation path on a live financial platform. It should be treated as an incident to close, not a backlog item. Not auto-fixed: Phase 3 rule 3.

### [M-003] `can_perform_action` returns NULL for any table with no permission row
- Severity: High
- Category: Security / Bug
- File or Source: `supabase/migrations/table_permissions.sql:64-78`
- Problem: unchanged since 2026-09-15 and still open. A missing `table_permissions` row makes `can_perform_action()` return NULL, which RLS evaluates as deny — safe by accident, not by design, and undiagnosable when it happens. The `documents` policies also delegate to `can_perform_action('companies', ...)`, so the populated `documents` row in the matrix is dead configuration an admin would reasonably expect to take effect.
- Recommended fix: wrap the result in `COALESCE(..., false)` to make the deny explicit, and point the `documents` policies at `can_perform_action('documents', ...)` or drop the unused row.

## IMPROVEMENT IDEAS

1. **Add a proceeds-conservation invariant to the waterfall engine today (M-001).** One assertion — holder proceeds must sum to the exit value — catches both leaks found this run and every future one, and it is cheap to add as both a runtime warning and a property-based test. The waterfall is the most consequential calculation on the platform and currently the least defended: three test cases, none exercising participation caps, and a warnings channel that the function hardcodes to empty. This is the single highest-value engineering change available right now.

2. **Close M-002 and add an RLS regression test.** Third consecutive run reporting the same unmitigated privilege-escalation path. After the migration lands, add a test that signs in as a `viewer` and asserts writes to `table_permissions`, `roles`, `investments` and `cap_table` all fail. RLS remains the only layer with neither compile-time nor unit-test coverage, and it is the layer holding the financial data.

3. **Make the two Settings pages dark-mode correct first (M-005).** They are the smallest files with the worst coverage (2 `dark:` usages each), so the fix is contained, and Security Settings is a page where a broken, low-contrast render actively undermines user confidence in the platform. Roughly an hour of work for the most visible quality win on the list.

4. **Stop the `select('*')` count from rising before fixing the existing 69 (M-007).** The count went up by one in two days, so a lint rule or PR-checklist item banning new unbounded selects is worth more than a one-time cleanup that will erode again. Pair it with the ESLint migration (M-004) so there is somewhere to put the rule.

5. **Type the `profile/page.tsx` boundary to force the `pipeline.status` casing drift into the open (M-008).** Define the stage names once as a `const` union in `lib/types.ts`, derive both UI labels and query filters from it, and delete the `as any[]`. This converts a class of silent zero-result bugs into compile errors, and it is the prerequisite for trusting anything the pipeline board reports.
