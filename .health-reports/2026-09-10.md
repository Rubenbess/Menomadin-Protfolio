## FIXED ISSUES

### [F-001] Every advanced-filter select option matched zero rows
- File: `lib/filter-utils.ts` (+ new `__tests__/filter-utils.test.ts`)
- Problem: `evaluateCondition` compares a filter option's `id` against the stored
  column value with strict equality. Four select fields had ids that match no stored
  value, so choosing any of them returned an empty list:
  - **`company.status`** offered `closed`, which is not in the `companies.status`
    CHECK constraint (`active`, `exited`, `written-off`, `watchlist`), and **omitted
    `written-off` and `watchlist`** — the two statuses that matter most for portfolio
    review could not be filtered at all.
  - **`company.sector`** offered `tech` / `healthcare` / `finance` / `consumer` /
    `energy`, while `normalizeSector` canonicalises stored sectors to `Healthtech`,
    `SaaS`, `Fintech`, `Cleantech`, `Consumer`, `Deep Tech`, `Marketplace`, `Other`.
    Not one id matched — `consumer` failed on case alone.
  - **`company.entry_stage`** offered snake_case `series_a` etc. against free-text
    values rendered verbatim in the UI as `Series A`.
  - **`contact.contact_type`** offered six lowercase ids against the
    `contacts.contact_type` CHECK domain (`Founder`, `Advisor`, `Co-investor`,
    `Service Provider`, `Other`). All six failed; `executive` and `investor` are not
    valid types at all, and `Co-investor` was missing.

  On a financial platform this is worse than a visible error: a partner filtering the
  portfolio to healthtech, or to written-off positions, sees an empty table and can
  reasonably conclude the fund holds none.
- Fix applied: aligned every option id to the domain actually persisted. Sector
  options are now derived from a new `CANONICAL_SECTORS` constant documented as
  needing to stay in sync with `SECTOR_ALIASES`; status mirrors the schema CHECK and
  the `CompanyStatus` union; `entry_stage` uses display-cased ids; `contact_type`
  mirrors its CHECK constraint. Each site carries a comment naming the constraint it
  mirrors and what the old ids matched.

  Added `__tests__/filter-utils.test.ts` — 8 tests that pin each select field to its
  schema domain, assert `normalizeSector` leaves every sector option unchanged, and
  round-trip a filter through `applyFilters` to prove a stored row is actually
  matched. This class of bug is silent by nature, so it needs a test rather than a
  reader's vigilance.

  Verified: `tsc --noEmit` clean, suite green at 118 tests (up from 110). No
  financial-calculation logic, schema, RLS policy, or auth path touched.

## MANUAL ACTION REQUIRED

### [M-001] `table_permissions` and `roles` have no RLS — any viewer can escalate to full delete rights
- Severity: **Critical**
- Category: Security
- File or Source: `supabase/migrations/table_permissions.sql` (Supabase — live DB state)
- Problem: This migration builds the platform's entire RBAC model. Every policy it
  creates on `companies`, `contacts`, `rounds`, `investments`, `cap_table`, `reserves`,
  `documents` and `pipeline` delegates to `can_perform_action()`, which reads its
  answer from the `table_permissions` table. That table — and the `roles` table beside
  it — are the only two tables in the whole schema that **never call `ALTER TABLE …
  ENABLE ROW LEVEL SECURITY`**.

  With RLS off, both are fully readable and writable by anyone holding the public anon
  key with a valid session. A user provisioned as `viewer` can run:

  ```sql
  update table_permissions
     set can_create = true, can_update = true, can_delete = true
   where role_name = 'viewer';
  ```

  and immediately hold destructive rights over every core financial table. The
  authorization matrix is self-modifiable by the least-privileged role, which means
  the RBAC model provides no security boundary at all.

  This is precisely the hole `20260618_secure_team_members.sql` was written to close —
  its own header comment cites `update team_members set role='admin' where id=<self>`
  as the attack. That fix hardened the role-*assignment* table and left the
  role-*definition* table open.

  Also note `get_user_role()` and `can_perform_action()` are `LANGUAGE SQL STABLE`
  **without `SECURITY DEFINER`**, so they read `table_permissions` as the calling user.
  This is why simply enabling RLS is not sufficient on its own — see the fix.
- Recommended fix: two coordinated changes, applied together.
  1. Make the helper functions read the matrix independently of the caller's own
     rights, so enabling RLS cannot brick authorization: recreate
     `can_perform_action(text, text)` and `get_user_role()` as
     `language sql stable security definer` with an explicit
     `set search_path = public` (required on any `security definer` function),
     keeping their existing bodies unchanged.
  2. Enable RLS and grant **read-only** access, leaving all writes to the service role:

  ```sql
  alter table public.table_permissions enable row level security;
  alter table public.roles             enable row level security;

  create policy "table_permissions_read" on public.table_permissions
    for select to authenticated using (true);
  create policy "roles_read" on public.roles
    for select to authenticated using (true);
  -- deliberately no insert/update/delete policy: the permission matrix is
  -- changed only via a migration or the service-role key, never by a client.
  ```

  Then verify from a `viewer` session that the `update` above fails, and that reads on
  `companies` still succeed. Ship this as a dated migration
  (`20260910_secure_table_permissions.sql`) and note the intentional absence of write
  policies in the file header, so a later reader does not "fix" it back open.

  Not auto-fixed: changing RLS policies is outside this check's mandate, and applying
  step 2 without step 1 would lock every non-admin out of the platform.

### [M-002] Two contradictory RLS regimes coexist; whichever applied last silently voids the RBAC matrix
- Severity: **Critical**
- Category: Security
- File or Source: `supabase/migrations/rls_tighten_team_members.sql` vs
  `supabase/migrations/table_permissions.sql` (Supabase — live DB state)
- Problem: Both migrations target the same 8 core tables with incompatible models,
  and **neither drops the other's policies**:
  - `table_permissions.sql` drops `authenticated_all` and creates a granular
    per-action set (`companies_read_policy`, `companies_delete_policy`, …) gated on
    the RBAC matrix.
  - `rls_tighten_team_members.sql` drops `authenticated_all` and creates a single
    `team_members_all` policy — `for all`, `using (exists (select 1 from team_members
    where id = auth.uid()))`.

  Postgres OR-combines permissive policies for the same command. So if both sets are
  present in the live database, `team_members_all` alone is enough to authorize any
  request from any registered team member, and the entire role matrix is dead code: a
  `viewer` gets full insert, update and **delete** on companies, rounds, investments,
  cap_table, reserves, documents, pipeline and contacts.

  Which state production is actually in cannot be determined from the repository,
  because the migration filenames carry no ordering (see the sub-issue below). The two
  files encode opposite intentions about what the security model *is*, which is the
  deeper problem.
- Recommended fix:
  1. Establish ground truth first — this is a read-only query, run it before changing
     anything:

  ```sql
  select tablename, policyname, cmd, permissive
    from pg_policies
   where schemaname = 'public'
   order by tablename, policyname;
  ```

  2. Decide which model is intended. The RBAC matrix is the richer one and the
     `roles`/`viewer` vocabulary is referenced by application code, so it is the
     likely keeper — but this is a product decision about whether Menomadin wants
     role-differentiated access or a flat team perimeter, and it should be made
     explicitly rather than inferred from migration order.
  3. Ship one dated migration that drops the losing policy set by name on all 8
     tables and leaves a header comment recording the decision, so the two models
     cannot silently re-converge.
  4. Sub-issue, worth fixing in the same pass: **19 of 21 files in
     `supabase/migrations/` have no date prefix**, so there is no deterministic apply
     order. For a database holding investment and cap-table records, a rename to
     `YYYYMMDD_*` (matching the two files that already do this) plus a short
     `supabase/migrations/README.md` recording applied order is cheap insurance.

  Not auto-fixed: resolving this requires live database state and a product decision.

### [M-003] Companies advanced filter offers MOIC and Total Invested, which do not exist on the data
- Severity: High
- Category: Bug
- File or Source: `lib/filter-utils.ts:165-175`, `app/(protected)/companies/CompaniesClient.tsx:150`
- Problem: `getFieldsForEntity('company')` offers numeric filters on `totalInvested`
  and `moic` with the full operator set including `between`. The `Company` interface in
  `lib/types.ts` has **neither field**, and `CompaniesClient` passes raw `Company` rows
  straight into `applyFilters`. `getNestedValue` therefore returns `undefined`, and
  every numeric comparison against `undefined` is `false` — `undefined > 3` and
  `undefined < 3` are both false.

  So "show me companies with MOIC above 3x" returns nothing, always. These are the two
  most valuable filters on the page for an investment team, and they are the two that
  cannot work. Same silent-empty-result failure mode as F-001, but the fix is not
  mechanical.
- Recommended fix: this is a design decision, which is why it was left untouched.
  Preferred: compute the metrics where the page already has the inputs and filter the
  enriched rows. `CompaniesClient` has access to investments and rounds, and
  `calcMOIC` / `calcTVPI` already exist in `lib/calculations.ts` — build a
  `useMemo`-derived `CompanyWithMetrics[]` (`{ ...company, totalInvested, moic }`) and
  pass *that* to `applyFilters`, keeping the metric definitions in the calculation
  layer rather than the filter layer. If that is out of scope for now, remove the two
  fields from `getFieldsForEntity` instead — an absent filter is honest, a
  permanently-empty one is not. Do not leave them as-is.

## IMPROVEMENT IDEAS

1. **Write a schema-vs-code domain check and run it in CI.** Today's F-001 was found by
   diffing hand-written TypeScript enums against SQL CHECK constraints. That diff is
   scriptable: parse `CHECK (col IN (...))` out of `schema.sql` and the migrations, and
   assert each corresponding TypeScript union and filter-option list matches. The same
   script would have caught all four F-001 sites and would catch the next drift on the
   day it lands. Highest leverage item on this list — it converts a recurring silent
   bug class into a build failure.

2. **Add an RLS coverage assertion to the same CI step.** The two Critical findings
   today were both found by programmatically sweeping RLS state across the schema, and
   both are invisible to `tsc` and `vitest`. Three cheap invariants would have caught
   them: every `CREATE TABLE` is followed somewhere by `ENABLE ROW LEVEL SECURITY`
   (catches M-001); every RLS-enabled table has at least one policy (already holds —
   worth locking); and no table carries two policies for the same command from
   different migrations without an intervening `DROP POLICY` (catches M-002). For a
   platform where RLS *is* the security boundary, this deserves to be a test rather
   than a monthly manual sweep.

3. **Make "silently empty" impossible in the filter UI.** The deepest lesson of F-001 is
   that on a financial platform, an empty result set is a claim about the portfolio —
   and it was wrong for a month. When `applyFilters` returns zero rows from a non-empty
   input, the Companies and Contacts pages should say *"No companies match these
   filters"* with a one-click clear, distinct from the *"No companies yet"* empty state.
   That single UI distinction turns a wrong conclusion into a visible question, and it
   is cheap: both pages already have the filtered and unfiltered counts in scope.

4. **Get the working tree committed, then keep it that way.** Seven reports of correct,
   green, undeployed fixes is now the platform's largest single risk — larger than any
   individual bug in it, because the bugs it fixes are all still live in production.
   Beyond landing it (M-004), consider a pre-existing-work check at the top of this
   daily task: if `git status` shows a working tree older than ~7 days, that becomes
   the report's lead finding rather than one entry among several.

5. **Give the daily check a way to see authenticated pages.** Phase 2 has been limited
   to unauthenticated perimeter checks for weeks because interactive login with MFA
   cannot complete unattended, which means the entire authenticated UI — dark mode,
   table responsiveness, loading and empty states, hydration on data-heavy pages — is
   never actually exercised. A dedicated read-only service account on a staging
   deployment, with TOTP seeded into an env var the task can consume, would restore
   real coverage of Phase 2's 1.5 and hydration checks. Worth scoping deliberately,
   since it means provisioning a credential specifically for automation.
