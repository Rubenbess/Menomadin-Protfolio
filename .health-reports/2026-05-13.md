## MANUAL ACTION REQUIRED

### [M-001] Cross-team RLS over-permissioning on the tasks subsystem
- Severity: **Critical**
- Category: Security
- Source: [supabase/migrations/tasks_system.sql:142-189](supabase/migrations/tasks_system.sql:142)
- Problem: Every policy on `tasks`, `task_assignees`, `task_comments`, `task_activities`, `task_attachments`, `task_labels`, `task_label_links`, `task_templates`, `task_recurrence_rules`, and `task_automation_rules` is defined as `for all to authenticated using (true) with check (true)`. The same `using (true)` pattern appears on `contacts.sql`, `contacts_crm.sql`, `global_documents.sql`, `notifications.sql`, and `deal_report_recipients.sql`. Today these tables don't have a `team_id` column, and every user defaults to `admin` in `team_members`, so the practical attack surface is currently "one Menomadin team member can read another's private notes / tasks / contact CRM history" — not external. Still, for a finance platform handling deal pipeline data, peer-to-peer read access by default is the wrong perimeter.
- Recommended fix: Introduce a `team_id` (or simpler: `created_by` ownership + an explicit "shared with team" boolean) on each table. Replace `using (true)` with `using (created_by = auth.uid() OR exists (select 1 from team_members tm where tm.user_id = auth.uid() and tm.role = 'admin'))`. Out of scope for auto-fix because it requires (a) a schema migration, (b) a backfill, and (c) a product decision on the share-by-default model.

### [M-002] Unbounded fetches on the three highest-cardinality list pages
- Severity: **Medium**
- Category: Performance
- Files: [app/(protected)/documents/page.tsx:11](app/(protected)/documents/page.tsx:11), [app/(protected)/tasks/page.tsx:15-30](app/(protected)/tasks/page.tsx:15), [app/(protected)/contacts/page.tsx:11](app/(protected)/contacts/page.tsx:11)
- Problem: All three pages `select(*)` (or near-`*`) and `order(...)` without `.limit()` or `.range()`. Today the row counts are small (internal portfolio platform, dozens of records), so the user-visible impact is nil. But the per-page server payload scales linearly with table growth, and a single CSV import that triggers the documents path could mint hundreds of rows in one stroke.
- Recommended fix: Cap at `.limit(500)` server-side and surface a "Showing 500 of N — use filters to refine" banner when the cap is hit, mirroring the pattern in `/api/search`. The `tasks/page.tsx` payload is the largest of the three (joins to `task_assignees`, `companies`, `pipeline`, `contacts`) and should be prioritised.

### [M-003] `tasks/page.tsx` renders raw error JSON on Supabase failure
- Severity: **Medium**
- Category: UI / Bug
- File: [app/(protected)/tasks/page.tsx:32-38](app/(protected)/tasks/page.tsx:32)
- Problem: When the tasks query fails, the page renders `<p>{error.message || JSON.stringify(error)}</p>` directly in production. This leaks raw Postgres / PostgREST error strings (table names, column hints) to anyone with a session, and gives no path to recovery. The other top-level pages either throw (handled by `error.tsx`) or render an empty list.
- Recommended fix: Either `throw new Error(...)` so the protected `error.tsx` boundary catches it, or render a user-friendly EmptyState with a Retry button (route revalidation). The current behaviour is the worst of both — it's user-facing but unreadable.

### [M-004] `CompanyCharts.tsx` ownership-% math accepts non-finite inputs
- Severity: **High**
- Category: Bug / Financial calc integrity
- File: `components/CompanyCharts.tsx` around the post-money × ownership multiply (~line 99 per the audit pass)
- Problem: The expression `Math.round((ownershipPct! / 100) * r.post_money)` non-null-asserts `ownershipPct` and trusts `r.post_money`. If either is `null`, `0`, or `NaN`, the rendered value silently becomes `NaN`. On a financial chart that's "showing 0" — but the underlying data is wrong, and the user has no signal.
- Recommended fix: Guard with `Number.isFinite(ownershipPct) && Number.isFinite(r.post_money) && r.post_money > 0` and render an em-dash placeholder when the guard fails. Same guard pattern is already established by `fmt$Nullable` in `lib/calculations.ts`.

### [M-005] `tasks/page.tsx` extracts `userId` without redirecting unauthenticated callers
- Severity: **Medium**
- Category: Auth
- File: [app/(protected)/tasks/page.tsx:11-12](app/(protected)/tasks/page.tsx:11)
- Problem: `const { data: { user } } = await supabase.auth.getUser()` then `const userId = user?.id || ''`. Middleware should keep unauthenticated users out of `(protected)`, but if it ever fails open, this page silently falls back to `userId = ''`, then renders the tasks list scoped to the empty string — visible to anyone. Belt-and-suspenders fix: redirect to `/login` when `!user`.
- Recommended fix: Add `if (!user) redirect('/login')` (import from `next/navigation`) before the queries fire. The same pattern would harden every protected server-component page that reads `user.id`.

### [M-006] Currency formatting still inline in two more places
- Severity: **Low**
- Category: Code quality
- Files: `app/(protected)/reports/ReportsClient.tsx:37-38`, `app/(protected)/profile/ProfileClient.tsx:474` (`'$' + (deal.fundraising_ask / 1e6).toFixed(1) + 'M'`)
- Problem: Two more inline `$x.yM` constructions that should call `fmt$$`. Not equivalent to `fmt$$` everywhere — these always force the M-suffix, while `fmt$$` chooses B/M/K based on magnitude. Worth confirming whether the caller actually wants always-millions or magnitude-adaptive before swapping.
- Recommended fix: If the values are always >= 1M (fundraising asks usually are), replace with `fmt$$(deal.fundraising_ask)`. Otherwise add an `fmt$Millions(n)` helper to `lib/calculations.ts` and use that.

### [M-007] `extract` API route trusts user-supplied `file_type` for the Anthropic media_type cast
- Severity: **Low**
- Category: Security (defensive)
- File: [app/api/extract/route.ts:78](app/api/extract/route.ts:78)
- Problem: `mediaType = (file_type?.startsWith('image/') ? file_type : `image/${ext}`)` is cast to the Anthropic-typed union. The URL is already allowlisted via `isAllowedFileUrl`, but `file_type` and `file_name` come straight from the client. A request with `file_type: 'image/exotic'` is passed through to the SDK; depending on the SDK's strictness, that's a 400 from upstream rather than a 400 from us. Not exploitable, just noisy.
- Recommended fix: Whitelist `mediaType` against the literal union (`image/jpeg|png|gif|webp`) and reject otherwise with a 400 before invoking the model. Cheap, removes a class of bad-request churn.

## IMPROVEMENT IDEAS

1. **Land the RLS tightening (M-001) as the next material piece of work.** This is the only Critical finding in today's pass and the only one that can leak data across users. The platform's "every team member is admin" default has been masking the issue; if Menomadin ever onboards an associate or LP-facing read-only user, every task / contact / global document the team has ever entered becomes visible by default. Designing the policy now — even before the role split — costs one migration and unblocks future user-tier expansion.

2. **Introduce a single `requireProtectedPage()` helper in `lib/api-auth.ts`** that does `getUser()` → `redirect('/login')` if missing → returns `{ supabase, user }`. M-005 generalises: every `(protected)/.../page.tsx` repeats the `auth.getUser()` dance, and at least the tasks page falls open on missing-user. Centralise once, retrofit each page in a follow-up sweep.

3. **Add a CI grep step that fails any `using (true)` outside a documented allowlist.** Yesterday's idea was an ESLint rule for dark-mode pairs; the analog for the RLS class would catch M-001's pattern at PR time. The grep is trivial — `git grep -nE 'using \(true\)' supabase/migrations` filtered against a `.rls-allowlist` text file.

4. **Pagination on the three big list pages (M-002) is a 30-line change once you pick a UX.** The simplest version is a server-side `.limit(500)` + an "Older items" link that bumps a `?offset=` param; the client never has to change. Pairs naturally with the existing `EmptyState` component.

5. **Decide the "magnitude-adaptive vs always-millions" rule for fundraising asks (M-006).** It's a one-line product call: do we want `$850K` to display as `$0.9M` for consistency, or as `$850K` because that's how the analyst typed it? Once decided, a small util (`fmt$Millions` or just using `fmt$$`) makes the next two-dozen places that touch fundraising figures look uniform.
