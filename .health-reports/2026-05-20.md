## FIXED ISSUES

### [F-001] Validate & normalise free-text Round Type server-side
- File: `actions/rounds.ts`
- Problem: Commit `62dc4b7` swapped the Round Type `<select>` for a free-text `<input list="…">`, but neither `createRound` nor `updateRound` trimmed the value or rejected empty/whitespace. The form's `required` is a browser-only guard — a direct server-action invocation (or any caller manipulating FormData) could land a whitespace-only `type`, which would then render as a blank bold label between the date and instrument badge on the company history tab (`CompanyDetailClient.tsx:661`). Sibling normalisation has existed for sectors (`normalizeSector` in `lib/calculations.ts`) for months; rounds had not caught up.
- Fix applied: Added a `normalizeRoundType()` helper (trim → reject empty → clamp to 80 chars). Both `createRound` and `updateRound` now route inbound `type` through it and return `{ error: 'Round type is required.' }` on empty input. The 80-char cap accommodates realistic compound names (e.g. "Series A-1 Extension (with new lead)") while bounding what can flow into the history-tab layout. Pairs cleanly with the existing `notes.slice(0, 5000)` guard.
- Verified: `npx tsc --noEmit` exit 0.

### [F-002] Render explicit error card when the Documents Vault page fails to load
- File: `app/(protected)/documents/page.tsx`
- Problem: The page fired `Promise.all([supabase.from('global_documents')…, supabase.from('companies')…])` and fed `.data ?? []` directly into the client component with no check on `.error`. ### [M-025] `convert_safe` RPC migration is untracked while the calling action has shipped
- Severity: **Critical**
- Category: Bug / Data Integrity
- File or Source: `supabase/migrations/convert_safe_rpc.sql` (untracked per `git status`), called from `actions/safes.ts:94` (`supabase.rpc('convert_safe', { … })`)
- Problem: The migration defines the atomic SAFE-conversion stored procedure (`security invoker`, marks the SAFE converted + inserts the cap-table row in a single transaction). The TypeScript caller has already replaced the previous best-effort JS rollback. If this branch deploys without applying the migration to the production Postgres, every SAFE conversion attempt 500s with `PGRST202: function public.convert_safe(...) does not exist`. The error path returns `rpcErr.message` directly to the UI (`actions/safes.ts:102`), so the user would see a raw Postgres error message — but no cap-table entry gets created, no audit trail, and the SAFE remains marked unconverted.
- Recommended fix: Two-step. **(1)** `git add supabase/migrations/convert_safe_rpc.sql` and commit it as part of the same logical group as the action's RPC call. **(2)** Before deploying, apply the migration to production Supabase — either `supabase db push` against the prod project, or paste the SQL into the Studio SQL editor and verify with `SELECT proname FROM pg_proc WHERE proname = 'convert_safe';`. Add a smoke test: convert one SAFE in staging end-to-end before merging.

### [M-027] Microsoft Graph OAuth tokens still stored plaintext (carryover M-017)
- Severity: **High**
- Category: Security
- File or Source: `app/api/auth/microsoft/callback/route.ts:85-95`, table `email_integrations`
- Problem: Same as M-017 on 2026-05-18. `access_token` and `refresh_token` are upserted as raw strings. Under today's permissive RLS (`team_members_all` policies allow every team member to read every row of `email_integrations`), any team member can read another team member's refresh token. Refresh tokens are long-lived (~90 days default with sliding refresh). A leaked Supabase backup, a misconfigured `pg_dump`, or a future RLS regression exposes inbox access for the remaining token lifetime. The most sensitive data the platform stores; still at-rest plaintext.
- Recommended fix: App-layer AES-256-GCM with a key in `process.env.EMAIL_TOKEN_KEY`. Encrypt before insert in the callback route; decrypt in `getValidAccessToken` (`lib/microsoft-graph.ts`). Migration to backfill is straightforward — read existing tokens, encrypt, update each row. Add a `last_rotated_at` column and a 30-day refresh-token rotation job at the same time.

## IMPROVEMENT IDEAS

1. **Commit-and-push gate as a daily-health-check pre-step.** Today's audit found that every M-series fix from 2026-05-18 is mechanically resolved but not deployed — production is running yesterday's bug surface for a week. A 5-line CI workflow that fails the build on any uncommitted files in the repo root (or alternatively, a one-shot script `.claude/hooks/pre-stop-warn-dirty.sh` that prints a red banner whenever a Claude session ends with a dirty tree) would prevent the audit-and-forget pattern from recurring. The platform already has automated weekly health checks; reading `git status` and refusing to claim "complete" on a dirty tree is the natural next step.

2. **Schema-vs-code invariant CI check** (carrying forward from 2026-05-18 Improvement #2 and now reinforced by today's M-025). Both the M-016 broken `assignee_id` write and today's M-025 untracked `convert_safe` migration are the same class of bug: TypeScript code calls a database object (column / function / index) that does not exist or does not yet exist in the deployed schema. A CI script that diffs `actions/**` + `app/api/**` against `supabase/migrations/**` and flags any `.from('TABLE').rpc('FN')` / `update({COL})` / `insert({COL})` reference whose target is not defined in a migration would catch this class at PR-time. Equally important: it would surface untracked migrations (M-025 is *visible* because of the audit, but normally `?? migration.sql` is easy to miss).

3. **Encrypt OAuth tokens AND rotate `companies.update_token` on use.** M-027 (still-plaintext Graph tokens) and the residual M-015 risk (founder-update token never rotates after a successful submission) can be addressed with a single shared rotation primitive: encrypt at rest with AES-256-GCM, generate a fresh opaque token on every consumption, invalidate the previous value. Apply to both `email_integrations.refresh_token` and `companies.update_token`. Two-day project. Closes the most embarrassing single security postmortem the platform could currently produce.

4. **Move the dirty-tree backlog onto a worktree so the dev branch can ship cleanly.** A pragmatic alternative to "commit it all today" (M-028): create a long-lived `cleanup/audit-backlog` worktree, move the entire uncommitted diff there, and ship from `main` going forward. Then carve the backlog into reviewable PRs at the team's own pace. Slower than the M-028 path but minimises merge risk on any individual chunk. Either approach is fine; doing *neither* (current state) is the bad outcome.

5. **Replace `window.confirm` + raw `opacity-0 group-hover:opacity-100` with a tiny shared primitives layer.** Today's U-001 found four more inline `confirm()` calls in `CompanyDetailClient.tsx`. The pattern is hereditary — every new destructive button gets one. Bundle `ConfirmDestructiveModal` (built on top of the existing `useConfirmDialog` hook) + a `<HoverRevealButton>` primitive with built-in `focus-visible` / `@media(hover:hover)` correctness + a `useDeleteAction(action, { successMsg, errorMsg })` hook into a single PR, then mass-replace existing call sites. Eliminates an entire category of future audit findings.
