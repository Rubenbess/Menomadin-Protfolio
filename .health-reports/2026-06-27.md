### [F-001] share_series financial fields accepted with no numeric validation
- File: actions/share-series.ts:9-50
- Problem: `createShareSeries` / `updateShareSeries` passed the payload straight to `insert`/`update`. Every numeric field here (`shares`, `price_per_share`, `invested_amount`, `liquidation_pref_mult`, `liquidation_seniority`, `participation_cap_mult`, `conversion_ratio`) feeds `buildWaterfallHolders` / `calcWaterfall`, where a `NaN`/`Infinity`/negative value silently corrupts the proceeds distribution. Server actions are directly invocable, bypassing any client-side form bounds. This was the share-series half of the 2026-06-18 finding M-012 — its four siblings (`cap-table`, `kpis`, `reserves`, `waterfall-scenarios`) were already validated in the working tree, leaving this file as the only un-guarded financial-write path.
- Fix applied: Added an `invalidShareSeries()` guard that runs `isInvalidMetric()` on every numeric field and returns `{ error: 'Share series values must be finite, non-negative numbers.' }` before any DB write, in both create and update. Mirrors the exact pattern already used in the sibling files. No upper caps on multiples were imposed (that would be a product decision).

### [F-002] option_pools financial fields accepted with no numeric validation
- File: actions/option-pools.ts:9-46
- Problem: Same class as F-001. `createOptionPool` / `updateOptionPool` wrote `shares_authorized`, `shares_issued`, `price_per_share` with no validation; these dilute the fully-diluted share total used by ownership and waterfall math, so a bad value cascades into those figures. This was the option-pools half of M-012.
- Fix applied: Added an `invalidOptionPool()` guard (`isInvalidMetric()` on the three numeric fields) returning a clean error before the write, in both create and update.

### [M-002] Waterfall: non-participating preferred conversion test ignores senior preferences *(CRITICAL — Financial)*
- Severity: Critical
- Category: Bug (Financial)
- File or Source: lib/calculations.ts:425-432 (`calcWaterfall`, verified still present this run)
- Problem: A non-participating preferred is marked "converting" when `asCommonValue = (commonEquiv / totalCommonEquiv) * exitValue` exceeds its liquidation preference — i.e. measured against the **full** exit. But a converter shares only the residual *after* senior preferences are paid. This tells junior preferred to convert in cases where its post-senior-pref common share is actually worth less than its preference, forfeiting a preference it should have taken — understating its proceeds and overstating common's. (2026-06-18 M-005; the working-tree waterfall changes fixed only the SAFE basis, not this test.)
- Recommended fix: Compare the preference against the holder's share of the residual after senior preferences (iterative/fixed-point), or at minimum against `(commonEquiv/totalCommonEquiv) * (exitValue − seniorPrefsAhead)`. Add a unit test with a senior + junior preferred stack where the naive test mis-converts.

### [M-003] Portfolio value / MOIC rest on an un-paired, position-derived ownership snapshot *(CRITICAL — Financial)*
- Severity: Critical
- Category: Bug (Financial)
- File or Source: lib/calculations.ts:32-34 (`calcCurrentValue`), 46-85 (`getFundOwnershipPct`/`calcCombinedOwnershipPct`); dashboard/analytics/reports per-company derivation
- Problem: The `[0,100]` clamp added in the working tree stops *impossible* values, but the underlying modelling issues from 2026-06-18 M-001/M-002/M-003 remain: (a) `calcCurrentValue` pairs the latest cap-table ownership % with the latest round's post-money with no guarantee the % is the snapshot as-of that round (dilution overstates value); (b) `getFundOwnershipPct` still identifies the fund row by **array position** (`capTable[length-1]`) with cap-table queries that have no `.order()`; (c) `calcCombinedOwnershipPct` still sums every matching row with no per-holder de-duplication (clamping masks, but does not fix, double-counting).
- Recommended fix: Carry `round_id`/`as_of_date` on cap-table rows and select the % effective at the latest round (or compute value from share counts × latest PPS); identify the fund row by an explicit `is_fund` marker or name match, never by position; de-duplicate to latest-per-holder before summing. This is the [I-2] shared-metrics module below.
