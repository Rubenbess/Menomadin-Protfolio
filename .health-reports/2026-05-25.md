### [M-025] `convert_safe` RPC migration still untracked while calling action has shipped (carryover, **Critical**, unchanged from 2026-05-20)
- Severity: **Critical**
- Category: Bug / Data Integrity
- File or Source: `supabase/migrations/convert_safe_rpc.sql` (untracked), `actions/safes.ts:94`
- Problem: The migration defines the atomic SAFE-conversion RPC (`security invoker`, marks SAFE converted + inserts the cap-table row in one transaction). The TypeScript caller has replaced its previous best-effort JS rollback. If `main` deploys to production without first applying the migration, every SAFE conversion attempt returns `PGRST202: function public.convert_safe(...) does not exist` (500), the SAFE remains marked unconverted, and no cap-table entry is created. Production has not yet seen either the new migration or the new caller (working tree dirty for 7 days), so the bug is latent — but the moment the diff lands, this is the first thing to break.
- Recommended fix: (1) Stage and commit `supabase/migrations/convert_safe_rpc.sql` in the same commit as the `actions/safes.ts` change. (2) Apply the migration to production Supabase via `supabase db push` or the Studio SQL editor *before* deploying the application code. (3) Verify with `select proname from pg_proc where proname = 'convert_safe';`. (4) Smoke-test one SAFE conversion in staging end-to-end before merging.

### [M-027] Microsoft Graph OAuth tokens still stored plaintext (carryover, High, unchanged)
- Severity: **High**
- Category: Security
- File or Source: `app/api/auth/microsoft/callback/route.ts:85-95`, table `email_integrations`
- Problem: `access_token` / `refresh_token` upserted as raw strings. Refresh tokens are ~90-day sliding. A leaked Postgres backup, a misconfigured `pg_dump`, or an RLS regression exposes inbox access for the remaining token lifetime. The most sensitive data in the platform; still at-rest plaintext. Detailed remediation in 2026-05-20 (M-027) and 2026-05-18 (M-017).
- Recommended fix: AES-256-GCM at the app layer with `process.env.EMAIL_TOKEN_KEY`. Encrypt before insert in the callback route; decrypt in `getValidAccessToken` (`lib/microsoft-graph.ts`). Add a `last_rotated_at` column and a 30-day rotation job. Backfill is a straightforward read-encrypt-write loop.

### [M-034] `/api/extract` has no bound on remote-file size — memory-exhaustion DoS possible
- Severity: Medium
- Category: Security / Performance
- File or Source: `app/api/extract/route.ts:44-45,60-61,79-80,103-104,124`
- Problem: Every extraction branch unconditionally calls `fileRes.arrayBuffer()` (or `fileRes.text()`) on the remote file. There is no `Content-Length` check, no streaming, and no max-size cap. A caller — even an authenticated one — who points `file_url` at an oversized but allowed-host file (e.g. a multi-GB stored document) will buffer the entire payload into Node's memory before the Anthropic call is dispatched. Vercel's serverless function memory limit (1024 MB by default for the Pro plan) means a single 800 MB request can OOM the lambda. The `isAllowedFileUrl` check earlier in the route limits the URL host but not the byte size. Authenticated-only, so the blast radius is internal — but a hostile employee or compromised account could brick the extract endpoint repeatedly.
- Recommended fix: After `fileRes.ok` succeeds, read `fileRes.headers.get('content-length')`, parse to int, reject anything over a reasonable cap (e.g. 25 MB — Anthropic's PDF input cap is 32 MB anyway). For unknown-length responses, switch to a streaming read with an in-flight byte counter and abort once the cap is exceeded. Mirror the pattern in `app/api/documents` if it shares the same shape.

### [M-035] `app/(protected)/companies/page.tsx` contacts query is unbounded
- Severity: Medium (forward-compat, low impact today)
- Category: Performance
- File or Source: `app/(protected)/companies/page.tsx:22-25`
- Problem: `supabase.from('contacts').select('*').in('company_id', ids)` — no `.limit()`. Today's portfolio has small contact counts so it doesn't matter, but the query is fed the entire `companies` ID list (also unbounded earlier in the same page), and contacts grow monotonically as new portfolio companies are added and as the contact directory expands. Every full-portfolio render touches this query. Sister page `app/(protected)/contacts/page.tsx:10-12` already caps at 500. Trivial to align.
- Recommended fix: Add `.limit(2000)` (or whatever upper bound is acceptable for the "linked contacts" panel) and consider `.select('id, name, company_id, position, contact_type')` to drop wide PII columns the companies page never renders. Same fix shape as 2026-05-20 M-030.

### [M-036] `app/api/auth/microsoft/callback` does not delete the nonce cookie on failed callbacks
- Severity: Low
- Category: Security
- File or Source: `app/api/auth/microsoft/callback/route.ts:13-46`
- Problem: The nonce cookie is only deleted on the success path (line 107). Every failure redirect (missing code, state mismatch, auth lookup error, mismatched user_id) leaves the cookie alive in the browser, where it can be replayed against a follow-up callback. Because the cookie is `HttpOnly` and the state in the redirect URL is the attacker's lever, the practical attack surface is narrow — but defense-in-depth says invalidate on every terminal outcome.
- Recommended fix: Wrap each `NextResponse.redirect(...)` in the failure paths with `const r = NextResponse.redirect(...); r.cookies.delete(NONCE_COOKIE); return r`. Five edits, one file, no test required.

## IMPROVEMENT IDEAS

1. **Make the deploy-gap visible.** The single most damaging pattern across the last three audits is "fix locally → mark fixed → never push → next audit re-flags as still-broken." A 2-line dashboard widget on the platform that shows "Working tree last pushed: X days ago" (read from `git log -1 origin/main` at build time, stored in a build artifact, exposed in a hidden admin route) would put the gap in front of the operator every time they log in, instead of buried in a git status output nobody runs. Pair with the CI "fail on dirty tree" gate suggested in 2026-05-20's IMPROVEMENT #1.

2. **Single-shot global dark-mode coverage audit.** F-001 (GlobalSearch), F-002 (DocumentUpload banner), M-033 (rest of DocumentUpload), and 2026-05-18 M-018 (dark-mode sweep) are all the same class — surfaces built before the dark-mode refactor and never visited again. A single `grep "bg-white"` / `grep "text-neutral-[89]00"` across `components/**` + `app/**` filtered to lines without an adjacent `dark:` would generate a closed list of remaining offenders. Estimated <40 sites. One PR closes the entire class.

3. **Standardise the dark-mode token palette in `lib/dark-mode-tokens.ts`.** The audits keep referencing the same handful of pairs — `bg-white / dark:bg-neutral-900`, `text-neutral-500 / dark:text-neutral-400`, `border-neutral-200 / dark:border-neutral-700`, `bg-gold-50 / dark:bg-gold-900/20`. Today every component re-types these by hand. A `surfaceClasses.card`, `surfaceClasses.bordered`, `surfaceClasses.muted` exports file would let future fixes be one-class swaps rather than four-variant decisions. Also documents the intended palette so design decisions don't drift component-by-component.

4. **Migrate the convert_safe RPC pattern to the rest of the transactional actions.** The atomic `convert_safe` RPC (M-025) is the *right* pattern — it eliminates the best-effort rollback that's been a recurring audit finding. `actions/safes.ts/convertSafe` got it; `actions/bulk-import.ts`, `actions/cap-table.ts`, and `actions/rounds.ts` (when creating a round + auto-creating an investment + auto-creating cap-table rows) all still do sequential writes with no compensating transaction. Carve out one Postgres function per multi-step action and migrate the action layer to RPC calls. Reduces the surface where "the SAFE/round/investment got created but the cap-table entry didn't" can happen.

5. **Stop calling `supabase.from('TABLE').select('*')` from page-level loaders.** Across `app/(protected)/contacts/page.tsx`, `app/(protected)/companies/page.tsx`, `app/(protected)/documents/page.tsx`, and several more, the SSR payload pulls the full row shape into the client bundle — including PII columns the client doesn't render. Same issue surfaced as M-030 (2026-05-20) and now M-035. A lint rule (or even a grep-based pre-commit check) that bans `.select('*')` outside `actions/` and `lib/` would force every page to declare its column list explicitly. Defence-in-depth, performance win, and PII-minimisation in one rule.
