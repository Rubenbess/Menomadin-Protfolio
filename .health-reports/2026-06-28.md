### [M-001] `team_members` RLS-hardening migration is UNTRACKED in git
- Severity: Critical
- Category: Security
- Source: supabase/migrations/20260618_secure_team_members.sql (shows as `??` untracked in `git status`)
- Problem: This is the only file that enables RLS on `team_members`, installs the anti-self-escalation guard trigger, and overrides the new-user default role. `team_members.role` is the authority behind `requireAdminAuth` and every `exists(select 1 from team_members …)` RLS policy. If it is not committed AND confirmed live, an authenticated browser client could `update team_members set role='admin' where id=<self>` and seize full read/write/delete over all portfolio, cap-table and investment data.
- Recommended fix: Commit the migration. Verify live: `select relrowsecurity from pg_class where relname='team_members'` must be `t`, and trigger `trg_enforce_team_member_role` must exist. Disable open signups in Supabase Auth as defense-in-depth.

### [M-002] `safes` table appears to have NO RLS in any tracked migration
- Severity: Critical
- Category: Security
- Source: supabase/migrations/safes_external_investors.sql:4; convert_safe_rpc.sql:24 (no `ENABLE ROW LEVEL SECURITY` for `safes` anywhere; `rls_tighten_team_members.sql` hardens 11 tables but omits `safes`)
- Problem: `safes` holds SAFE instruments (investor, valuation cap, conversion shares/price) — core deal financials. Postgres defaults RLS off, so unless enabled out-of-repo the table is readable/writable by anyone holding the public `anon` key shipped to every browser.
- Recommended fix: Verify `select relrowsecurity from pg_class where relname='safes'`; if false, `ALTER TABLE safes ENABLE ROW LEVEL SECURITY` plus a team-member membership policy mirroring the core tables. Consider `revoke execute on function convert_safe(...) from anon, public`.

### [M-003] DPI is hardcoded to zero on the dashboard and LP report
- Severity: Critical
- Category: Bug (Financial calculation)
- File: app/(protected)/dashboard/page.tsx:124 and app/(protected)/analytics/page.tsx:82
- Problem: `const dpi = calcDPI(0, totalInvested)` — the distributions argument is the literal `0`, so DPI always renders `0.00x`. This is shown prominently to LPs (dashboard + LP report PDF). It is a false metric, not a "no data yet" state.
- Recommended fix: Aggregate real distribution/realized-exit data and pass that sum to `calcDPI`. If no distributions data model exists yet, **hide** the metric rather than display a false `0.00x`.

### [M-004] Written-off / exited companies are still valued at their last-round mark → IRR & MOIC overstated
- Severity: Critical
- Category: Bug (Financial calculation)
- File: app/(protected)/dashboard/page.tsx:101 and app/(protected)/analytics/page.tsx (parallel logic)
- Problem: `currentValue = latestRound ? calcCurrentValue(ownershipPct, latestRound.post_money) : 0` with no check on `status`. A `written-off` company still contributes a positive terminal value to portfolio MOIC/TVPI and to the single synthetic XIRR inflow, inflating reported returns. Exited companies should reflect realized proceeds, not the last private mark.
- Recommended fix: Zero `currentValue` for `status === 'written-off'`; for `status === 'exited'`, use realized proceeds. Confirm where realized proceeds/distributions are stored before implementing.

### [M-005] `calcCurrentValue` has no finiteness guard → one bad row NaN-poisons every portfolio aggregate
- Severity: Critical
- Category: Bug (Financial calculation)
- File: lib/calculations.ts:32-34
- Problem: `(ownershipPct / 100) * latestPostMoney` with no `Number.isFinite` guard. If a legacy `rounds.post_money` is `null`/`NaN` (the validation guard in `rounds.ts` only applies to new writes), `currentValue` becomes `NaN`, which propagates into `calcMOIC`, `totalCurrentValue` (`reduce` → NaN), TVPI and the portfolio XIRR terminal inflow — silently corrupting every top-line number.
- Recommended fix: `if (!Number.isFinite(ownershipPct) || !Number.isFinite(latestPostMoney)) return 0`. **This is a purely defensive guard with no behavior change on valid inputs — safe to approve quickly.** Flagged rather than auto-applied only because Phase 3 rules require confirmation before touching financial-calc code. Consider mirroring a finiteness check in `calcMOIC`/`calcTVPI`/`calcDPI` numerators and in `fmtPct`/`fmtMultiple` (which render `"NaN%"`/`"NaNx"`).

### [M-006] Waterfall drops cap-excess proceeds when there is no uncapped common → payouts sum to less than exit value
- Severity: Critical
- Category: Bug (Financial calculation)
- File: lib/calculations.ts:500-512 (`calcWaterfall`)
- Problem: When participation caps trigger, `capExcess` is redistributed only to uncapped common. If `uncappedEquiv === 0` (all-participating-capped stack, or zero common shares), the `if` is skipped and `capExcess` is silently dropped. The function still returns `{ totalProceeds: exitValue }`, so `WaterfallScenarioPanel.tsx` (h.proceeds / totalProceeds) renders bars that don't sum to 100% — money disappears. The only sum-to-100% test uses a single common holder, so this path is untested.
- Recommended fix: When no uncapped common exists, redistribute `capExcess` pro-rata to remaining uncapped participants, and if everyone is capped, fall back to pro-rata by issued shares so `sum(proceeds) === exitValue`. Add an invariant test asserting `sum(proceeds) ≈ exitValue`.

### [M-007] Waterfall conversion decision uses gross exit value, and cap enforcement is single-pass
- Severity: Critical
- Category: Bug (Financial calculation)
- File: lib/calculations.ts:468-471 (conversion test) and :485-512 (cap enforcement)
- Problem: A non-participating preferred holder's "convert vs take preference" decision is judged against the **full exit value**, but if it converts it actually shares only the **residual** after senior preferences — so in a multi-tranche stack a holder flagged "convert" can receive less than its preference (the opposite of what the test intends). Separately, cap enforcement is a single pass that never iterates to a fixed point, so excess from one capped tier is not offered to an under-cap tier. Both produce misallocated proceeds in multi-tier stacks; neither path is tested.
- Recommended fix: Iterate the conversion decision against each holder's actual residual payout, and loop cap-application + redistribution until `capExcess` converges. Confirm intended waterfall semantics with the business before changing.

## IMPROVEMENT IDEAS
1. **Add a `sum(proceeds) === exitValue` invariant test to the waterfall, plus multi-tier seniority / participation-cap cases.** The waterfall (M-006/M-007) is the most financially consequential and least-tested surface — the only payout tests are a single common holder and a single sub-pref preferred. A property-style invariant test would have caught the cap-excess drop immediately.
2. **Build a realized-distributions data model and wire it through DPI + IRR + exited/written-off marks (M-003/M-004/M-008).** These three findings share one root cause: the platform tracks invested capital and current marks but has no realized cash-flow concept, so DPI is faked as 0 and dead companies inflate returns. This is the single highest-leverage data-model investment for LP-facing accuracy.
3. **Adopt a `loadGuarded()` data-fetch wrapper for server pages and a thin `actionGuard()` for server actions.** The two largest finding clusters — pages swallowing `.error` (M-014) and actions missing `getUser()` (today's 8 fixes + M-029) — are both "everyone reimplements the boilerplate and some forget." A shared helper that throws on error / rejects unauthenticated would make the safe path the default and let `tsc` catch omissions.
4. **Configure ESLint for real and add it to CI.** `next lint` currently only opens an interactive setup prompt, so no linting runs in scheduled/CI contexts — `no-floating-promises`, `react-hooks/exhaustive-deps` and `no-explicit-any` rules would have surfaced M-015/M-025/M-030 automatically. Migrate to the flat-config ESLint CLI and gate the build on it.
5. **Reconcile the RLS migrations into one authoritative, committed, role-aware model and verify it live.** The recurring Critical RLS findings (M-001/M-002/M-020/M-021/M-022) all stem from layered, partially-contradictory migrations whose live state is unknown. A single consolidated migration plus a checked-in `select relrowsecurity …` verification script (run against prod) would convert "we think it's secure" into "we can prove it."
