## FIXED ISSUES

### [F-001] Pipeline create: missing null guard on insert result
- File: actions/pipeline.ts:31
- Problem: `createPipelineEntry` checked only `error` then accessed `row.id`. If the insert returns no row (e.g. an RLS `WITH CHECK` silently filtering the `RETURNING` row), `row` is null and `row.id` throws an opaque 500 instead of a clean error. Every sibling action (`companies`, `contacts`, `global-documents`) guards with `error || !row`.
- Fix applied: Changed to `if (error || !row) return { error: error?.message ?? 'Pipeline entry not created', id: null }`.

### [F-002] Kanban board (Tasks) drops all updates after mount

- Fix applied: Added `import { useEffect }` and `useEffect(() => { setLocalTasks(groupedTasks) }, [groupedTasks])` to re-sync on prop change.

### [M-001] Portfolio value & MOIC pair an un-matched ownership % with a round's post-money
- Severity: Critical
- Category: Bug (Financial)
- File or Source: lib/calculations.ts:32-34; app/(protected)/dashboard/page.tsx:101-102; app/(protected)/analytics/page.tsx:59-60
- Problem: `calcCurrentValue = (ownershipPct/100) * latestPostMoney`. `ownershipPct` is the latest cap-table %, but `latestPostMoney` is the post-money of the latest-dated round — there is no guarantee the % is the snapshot as-of that round. If a newer round diluted the fund while the cap-table row still holds the pre-dilution %, current value is overstated, and this is the single number LPs see as "Portfolio Value," feeding TVPI/MOIC/IRR.
- Recommended fix: Pair the ownership snapshot to the round it belongs to (carry `round_id`/`as_of_date` on cap-table rows and select the % effective at `latestRound.date`), or compute current value from share counts × latest price-per-share. At minimum, enforce and document the invariant that the fund cap-table row is updated on every round.

### [M-002] Fund ownership read from "last array element" — order-dependent
- Severity: Critical
- Category: Bug (Financial)
- File or Source: lib/calculations.ts:47-51 (`getFundOwnershipPct`)
- Problem: Returns `capTable[capTable.length - 1].ownership_percentage`. The cap-table queries (dashboard/analytics/reports) use `.select('*')` with no `.order()`, so row order is not guaranteed. The "add the fund entry last" comment is not enforceable. When `calcCombinedOwnershipPct` finds no entity alias it falls back to this, so a mis-ordered cap table can use a different shareholder's % as the fund's.
- Recommended fix: Identify the fund row explicitly (match the fund/legal-entity name or add an `is_fund` boolean column), never by array position. If position is unavoidable, add an explicit `.order()` and a typed marker.

### [M-003] Combined ownership % can double-count past 100%
- Severity: Critical
- Category: Bug (Financial)
- File or Source: lib/calculations.ts:59-71 (`calcCombinedOwnershipPct`)
- Problem: Sums every cap-table row whose `shareholder_name` matches an entity alias, then sums across entities, with no dedup or upper bound. With one row per round per holder (common) or a shared alias, the same stake is counted multiple times and the combined % can exceed 100, multiplying `latestPostMoney` into an impossible current value. The single-row create guard (cap-table.ts:18) caps one row at 100 but never the sum.
- Recommended fix: Deduplicate to latest-per-holder before summing and clamp to `[0,100]` (or surface an error if the sum exceeds 100, since that signals stale rows).

### [M-004] Waterfall fabricates SAFE share count on an incompatible unit basis
- Severity: Critical
- Category: Bug (Financial)
- File or Source: lib/calculations.ts:339-352 (`buildWaterfallHolders`)
- Problem: An unconverted-capped SAFE's share count is invented as `Math.round((investment/cap) * 1_000_000)`. The `1e6` scalar is unrelated to the company's actual share units used by real `ShareSeries` holders, yet `calcWaterfall` distributes residual pro-rata by `shares * conversionRatio` across all holders — so the SAFE competes against real share counts on the wrong scale, misallocating proceeds whenever a capped SAFE coexists with real series.
- Recommended fix: Convert the SAFE to shares on the same basis as the cap table — `safeShares = investment / pricePerShare`, where PPS derives from the cap and the pre-round fully-diluted share count — so units match `ShareSeries.shares`.

### [M-005] Non-participating preferred conversion test ignores senior preferences
- Severity: Critical
- Category: Bug (Financial)
- File or Source: lib/calculations.ts:374-383
- Problem: A non-participating preferred is marked "converting" if its as-converted value computed against the **full** exit (`(commonEquiv/totalCommonEquiv) * exitValue`) exceeds its liquidation preference. But a converter shares only the residual after senior prefs are paid. Comparing against the gross exit tells junior preferred to convert in cases where post-senior-pref common conversion actually yields less than its preference, so it forfeits a preference it should have taken — understating its proceeds and overstating common's.
- Recommended fix: Compare the preference against the holder's share of the residual after senior preferences (an iterative/fixed-point calculation), or at minimum against `(commonEquiv/totalCommonEquiv) * (exitValue − seniorPrefsAhead)`.

### [M-006] IRR (XIRR) has no bisection fallback — silently blanks/zeros valid IRRs
- Severity: Critical
- Category: Bug (Financial)
- File or Source: lib/calculations.ts:111-121; coerced to 0 at app/(protected)/analytics/page.tsx:81
- Problem: Pure Newton-Raphson from a fixed 0.15 seed. For flat/curved NPV near the root or multiple sign changes it can oscillate, shoot out of range, or hit a near-zero derivative and return `null`. The dashboard then shows "N/A" (acceptable) but analytics coerces `null → 0%`, understating fund performance with a confidently-wrong number.
- Recommended fix: Wrap Newton in a bracketing/bisection fallback over a wide rate interval (≈ -0.9999 to 100) when it fails to converge; render non-convergence as "N/A" everywhere (don't coerce to 0).

### [M-007] Top/under-performer lists default MOIC to 1, hiding write-offs
- Severity: Critical
- Category: Bug (Financial)
- File or Source: lib/analytics-utils.ts:102,118 (`c.moic || 1`)
- Problem: A legitimately-zero MOIC (written-off company, current value 0) is coerced to 1.0x (break-even). `getUnderperformers`'s `moic < 1` filter then **excludes** genuine zeros, so a fully written-off company never appears as an underperformer, and `getTopPerformers` inflates a 0x company to 1x.
- Recommended fix: Distinguish missing from zero — use `c.moic ?? null`, filter null (unknown) separately, and ensure the underperformer filter includes `moic === 0`.

### [M-008] `team_members` table has NO Row-Level Security — browser-level privilege escalation
- Severity: Critical
- Category: Security
- File or Source: Supabase / supabase/migrations/handle_new_user_trigger.sql:13-21 (no `ENABLE ROW LEVEL SECURITY` for `team_members` exists in any tracked migration or schema.sql)
- Problem: `team_members` is the role-authority table read by `get_user_role()`, `requireAdminAuth`, and every admin gate. With RLS off, the browser anon/authenticated client can run `supabase.from('team_members').update({ role: 'admin' }).eq('id', myUserId)` directly, bypassing all server-action guards: a user can self-escalate to admin, overwrite any member's role/email, and read every member's email. Verify on the live DB, not just in migrations.

### [M-010] MFA is enforced only in middleware, not on Server Actions or `/api/` routes
- Severity: High
- Category: Security
- File or Source: middleware.ts:58-75 (only AAL check in the codebase); lib/api-auth.ts:17-26 (`requireAuth` checks session, not AAL); app/(protected)/layout.tsx (no AAL check)

## IMPROVEMENT IDEAS
(Prioritized, specific to what was observed.)

1. **Lock the database perimeter to match the (already-strong) app layer.** The app does everything right — `getUser()` everywhere, fail-closed guards, encrypted tokens — but M-008/M-009/M-016/M-018 mean RLS is the weak link. Run a one-time RLS audit script in CI that asserts every table has RLS enabled and no `USING(true)` write policy survives, plus a smoke test that an anon client cannot `update` `team_members`. This is the single highest-leverage hardening for a financial platform.

2. **Extract a single `lib/portfolio-metrics.ts` source of truth.** M-001–M-003, M-007, M-014, M-021, M-022 all stem from financial logic being re-derived inline across dashboard/analytics/reports/LP pages with subtle divergence. One audited, unit-tested module that takes the raw tables and returns `CompanyWithMetrics[]` (with the ownership-snapshot/round pairing fixed once) would eliminate "the dashboard and the LP report disagree" — unacceptable on a fund platform — and give the calc bugs a single place to fix and test.

3. **Make MFA a real data boundary, then add a thin authenticated E2E smoke test.** M-010 means MFA is currently a redirect, not enforcement. After moving the AAL check into `requireAuth`/RLS, add a Playwright (or similar) login+MFA smoke run against a seeded test account so future daily health checks can actually exercise the authenticated app (today the whole app is un-testable unattended behind login+MFA — Phase 2 here was limited to the public surface).

4. **Add input-validation parity + a shared `fetchWithSizeCap`/error-hygiene helper for all remote-fetch and financial-write paths.** M-012 (share-series/option-pools), M-019/M-020 (imports) show validation/hardening was applied per-file rather than systematically. Promote `isInvalidMetric` to mandatory on every financial insert and export the `fetchWithSizeCap` + generic-error pattern (now in extract and, post-fix, analyze-deck) into `lib/` so no future route reinvents it leakily.

5. **Tighten the founder-update capability.** M-011: add token expiry + single-use submission nonce and move the public `/updates/[token]` route off the service-role key onto a scoped anon RLS policy. Founder-submitted KPIs flow into LP reports, so a poisoned or replayed submission is a data-integrity issue, not just an access one.
