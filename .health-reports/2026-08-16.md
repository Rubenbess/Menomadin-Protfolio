## PHASE 3 — AUTO-FIXES APPLIED

### [F-001] `localDateKey` is a no-op on the server; Jerusalem-anchored helpers added
- Files: `lib/date-utils.ts`, `app/api/cron/reminders/route.ts`,
  `actions/task-recurrence.ts`, `actions/task-automations.ts`,
  `app/api/send-report/route.ts`, `__tests__/date-utils.test.ts`
- Problem: The timezone remediation in the working tree introduced `localDateKey()`,
  which formats a `Date` using the **runtime's own** timezone. In the browser that is the
  user's timezone, which is exactly right — and all thirteen client-side call sites are
  correct. But on Vercel the Node process runs in **UTC**, so in server code
  `localDateKey()` is byte-for-byte equivalent to the `toISOString().split('T')[0]` idiom
  it was written to replace. The helper's own doc comment warns about this bug class
  while the helper silently reproduces it server-side.

  Five server call sites were affected. The impact is a one-day error for anything
  executing between Israeli midnight and 02:00/03:00:
  - `app/api/cron/reminders/route.ts:36` computed "today" for the
    `.lte('due_date', today)` filter. The scheduled fire is 07:00 UTC (10:00 Israel), so
    the daily run is unaffected — but a retry or manual invocation after Israeli midnight
    would read yesterday's date and **silently skip a day's due reminders**.
  - `actions/task-recurrence.ts:101,118,119` wrote `due_date`, `next_occurrence`, and
    `last_generated` on recurring tasks. These are user-triggered server actions running
    at arbitrary hours, so a task generated late in the Israeli evening would be
    **persisted with the wrong due date**, and `last_generated` could mis-stamp the day,
    risking a duplicate or skipped generation.
  - `actions/task-automations.ts:143` wrote `due_date` on automation-created tasks, same
    exposure.
  - `app/api/send-report/route.ts:56` dated the weekly deal report email subject.
- Fix applied: Added `jerusalemDateKey(d)` and `todayJerusalem()` to `lib/date-utils.ts`,
  built on `Intl.DateTimeFormat('en-CA', { timeZone: 'Asia/Jerusalem' })` — which handles
  the UTC+2/UTC+3 DST transition automatically rather than hardcoding an offset. The
  formatter is constructed once at module scope, since `Intl` construction is not cheap
  and these run in hot server paths. Documented on the export why server code must not
  reach for `localDateKey`. Swapped all five server call sites over. Left every
  client-side `todayLocal`/`localDateKey`/`addDaysLocal` call untouched — those are
  correct as written, and switching them to a hardcoded Israel timezone would be a
  product decision, not a bug fix.

  Added five tests asserting against **absolute UTC instants**, so they hold regardless of
  the runner's timezone: the winter (UTC+2) rollover at 22:00Z, the summer DST (UTC+3)
  rollover an hour earlier at 21:00Z, and the boundaries either side. The 22:30Z winter
  case is precisely the one the old idiom gets wrong.
- Verification: `tsc --noEmit` clean; suite green at **110 passed** (was 105). The raw
  idiom now appears nowhere in `app/`, `actions/`, `lib/`, or `components/`.
- Scope note: this changes no financial calculation and no authentication flow. It does
  change the calendar day written to `due_date` for late-evening Israeli activity — which
  is the entire point of the fix.

### [M-002] No lint rule prevents the UTC date idiom from returning
- Severity: Medium
- Category: Code Quality
- File or Source: repo-wide; ESLint config
- Problem: F-001 is the fourth distinct defect from this one idiom. The codebase is clean
  today, but nothing stops the next hand-written `toISOString().split('T')[0]` — or, now,
  the subtler mistake of calling `localDateKey` from server code.
- Recommended fix: Add a `no-restricted-syntax` rule banning
  `MemberExpression[object.callee.property.name='toISOString']` outside
  `lib/date-utils.ts`, with a message pointing at the helpers. Consider additionally

  server/client distinction bites. This depends on ESLint being runnable — see M-004 from

### [M-003] Sanitized email HTML has no rendering-side defence in depth
- Severity: Medium
- Category: Security
- File or Source: `components/TaskEmailAttachmentDisplay.tsx:144`
- Problem: Sanitization happens once, at ingest, in `lib/email-snapshot.ts`. That is the
  right primary control and it is correctly configured. But the stored value is trusted
  unconditionally at render time, so the security of an authenticated session rests on
  every historical row having passed through the current sanitizer. Any row written
  before the sanitizer existed, imported by another path, or written directly to
  `task_email_attachments` bypasses it entirely. Flagged Medium rather than High because
  no bypass path is currently known to exist.
- Recommended fix: Either re-sanitize at render (client-side DOMPurify is cheap for a
  collapsed panel that is only expanded on demand), or render the body inside a sandboxed
  `<iframe srcdoc>` with `sandbox="allow-popups allow-popups-to-escape-sandbox"` and no
  `allow-scripts`. The iframe also fixes a real UX problem: hostile or merely
  badly-authored email CSS currently renders in the same document as the app.

### [M-004] Supabase RLS policies remain unverified
- Severity: High
- Category: Security
- File or Source: Supabase
- Problem: Carried unresolved across every report since 2026-07-28. This run has no
  database access, so no table's read/write policy can be confirmed. On a platform
  holding cap tables, valuations, and LP reporting data, an unreviewed RLS surface is the
  single largest unquantified risk in the system. The migrations
  `rls_tighten_team_members.sql`, `20260618_secure_team_members.sql`, and
  `table_permissions.sql` show active hardening, and the documented service-role read at
  `app/api/cron/reminders/route.ts:28-31` is a deliberate, correctly-reasoned exception —
  but none of that substitutes for reading the live policy set.
- Recommended fix: Commit a script that dumps `pg_policies` against production using the
  service-role key and asserts an expected-policy snapshot, then wire it into this daily
  check. That converts a perpetually-deferred manual review into a pass/fail signal that
  catches a policy regression the day it lands.

### [M-005] Authenticated runtime surface is never exercised
- Severity: Medium
- Category: Process
- File or Source: Runtime

## IMPROVEMENT IDEAS

1. **Ship what is already fixed.** M-001 is the highest-leverage item on this list by a
   wide margin. Roughly two weeks of correct, tested, type-clean remediation is sitting
   in a working tree delivering zero value to users. Nothing else in this report improves
   the live platform as much as committing and deploying today.

2. **Make the client/server timezone split structurally impossible.** F-001 was a fix
   that introduced a subtler version of the bug it fixed, which is a strong signal that
   the distinction is too easy to get wrong by hand. Beyond the lint rule in M-002,
   consider renaming the client helpers to `browserDateKey`/`todayInBrowser` so the name
   itself refuses to read correctly in a server action, and export `todayJerusalem` as
   the obvious default for anything writing to the database.

3. **Anchor the database to one calendar convention and write it down.** `due_date`,
   `next_occurrence`, `last_generated`, and KPI `date` are all bare `YYYY-MM-DD` columns
   whose intended timezone is implicit. F-001 fixed the writers, but a client-side
   `todayLocal()` default in `ReminderForm` and a server-side `todayJerusalem()` in
   `task-automations` can still disagree for a user travelling outside Israel. Decide
   explicitly that these columns mean "Israel calendar day", document it beside the
   helpers, and make the forms use the same anchor.

4. **Turn the RLS audit into a committed, runnable assertion.** Restating M-004 as an
   idea because it is the item most worth engineering effort: a `pg_policies` snapshot
   test would retire a finding that has now been carried, unresolved, across five
   consecutive reports — and would upgrade this daily check from "reads code" to
   "verifies production posture".

5. **Property-test the money paths.** `lib/calculations.ts` carries visible scar tissue
   from real defects — write-off valuation, positional cap-table reads, DPI honesty,
   negative-currency formatting, and today's `calcFullyDilutedShares`/SAFE clarification.
   The 110-test suite is a genuine asset; extend it with invariants rather than more
   examples: ownership always within `[0, 100]`, MOIC/TVPI never `NaN` or `Infinity`,
   waterfall payouts summing exactly to exit value. The waterfall remains the most
   intricate and least directly covered logic in the codebase.
