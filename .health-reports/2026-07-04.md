## FIXED ISSUES

### [F-001] Audit trail silently drops `0` and `false` field changes
- File: `actions/activities.ts:43-44`
- Problem: `old_value: oldValue ? String(oldValue) : null` used truthiness, so a legitimate change *to* `0` or `false` (exactly the numeric/boolean edits a financial platform must record) was written as `null` — a corrupted, misleading audit log.
- Fix applied: switched both `old_value`/`new_value` to `!= null` guards so `0`/`false` are recorded; added an explanatory comment.

### [F-002] `getAutomationRules` had no authentication guard
- File: `actions/task-automations.ts:84`
- Problem: Unlike its three sibling mutations, `getAutomationRules` selected `task_automation_rules` with no `getUser()` check — read protection rested entirely on RLS with no defense-in-depth.
- Fix applied: added the standard `const { data: { user } } = await supabase.auth.getUser(); if (!user) return { error: 'Not authenticated' }` guard, matching the rest of the file.

### [F-003] Global search debounce timer leaked on unmount (setState-after-unmount)
- File: `components/GlobalSearch.tsx:60` (new cleanup effect)
- Problem: `handleInput` scheduled `setTimeout(() => search(q), 200)` but no cleanup cleared a pending timer on unmount; the fetch was aborted but a queued `search()` could still fire `setState` on an unmounted component.
- Fix applied: added a mount-scoped `useEffect(() => () => { if (debounceRef.current) clearTimeout(debounceRef.current) }, [])`.

### [F-004] LP report crashes on a null valuation (no LP email sent) + renders `$NaN`
- File: `app/api/cron/lp-report/route.ts:6,62,79,93`
- Problem: `fmt$$(latestRound.post_money)` was guarded only by "a round exists," not "post_money is non-null." `fmt$$` ends in `amount.toLocaleString()`, so a null `post_money` threw `TypeError` inside `.map().join('')`, crashing the whole handler — the quarterly LP update was never sent. The `totalInvested`/per-company `inv` sums also became `NaN` (rendered `$NaN`) if any `amount` was null.
- Fix applied: import and use the existing `fmt$Nullable(latestRound?.post_money) ?? '—'`; null-coalesce the two reduces (`i.amount ?? 0`) and widen their row types to `amount: number | null`. Display/null-safety only — no change to any calculation's intent.

### [F-005] Information disclosure — raw Supabase/exception messages returned to clients
- Files (10 sites): `app/api/documents/route.ts:39,49` · `app/api/kpi-import/route.ts:30` · `app/api/task-templates/route.ts:29` · `app/api/task-templates/[id]/route.ts:70,109` · `app/api/import/csv/route.ts:85,124` · `app/api/tasks/emails/route.ts:30,68,100` · `app/api/import/trello/route.ts:111` · `app/api/extract/route.ts:178`
- Problem: These returned the verbatim Postgres/PostgREST error string (or raw exception `.message`) to the caller. Supabase errors routinely include column/constraint names and RLS hints — handing an attacker the schema/RLS structure to probe. Directly contradicts the intent of prior commit `0f84e1c` ("stop leaking internal error details").
- Fix applied: each site now `console.error`s the real error server-side and returns a fixed generic client message (e.g. "Could not save document", "Invalid form data"). Status codes unchanged.

#### [M-007] RLS policy layering + default-admin signup trigger are unverifiable and order-dependent
- Severity: Critical · Category: Security (broken access control / privilege escalation)
- Source: `schema.sql:99-105` (`authenticated_all USING(true)`) · `supabase/migrations/table_permissions.sql:92-236` · `rls_tighten_team_members.sql:19-133` · `handle_new_user_trigger.sql:6-24` (every signup → `admin`) vs `20260618_secure_team_members.sql:151-178` (hardened: first user admin, rest viewer, `@menomadin.com` gate).
- Problem: PostgreSQL policies are permissive (OR-combined). Multiple migrations add differently-named policies to the same financial tables; all are "apply manually in the SQL editor" scripts with **no version ledger or ordering guarantee**. If applied out of order/partially, the effective policy set is the union — a residual `USING(true)` or the default-admin trigger could still be live, and combined they are total compromise (any signup → admin → reads all financial tables).
- Recommended fix: Consolidate to one authoritative migration per table (DROP all prior policies by name first), delete `handle_new_user_trigger.sql` from the repo, adopt numeric-prefixed ordered migrations + a migrations ledger, and verify live `pg_policies.qual` has no `true` on `companies`/`investments`/`cap_table`/`rounds` and `pg_proc` shows the domain-gated `handle_new_user`. **Note:** `team_members` role self-escalation IS correctly blocked by the `enforce_team_member_role()` trigger — *provided* the hardened migration is the live one.

## IMPROVEMENT IDEAS (prioritized, platform-specific)

1. **Establish an ordered, ledgered migration workflow + a live-RLS assertion.** The single biggest risk source is that every RLS/trigger change is a hand-applied SQL script with no ordering guarantee, making M-006/M-007 unverifiable. Adopt numeric-prefixed migrations, a migrations ledger table, and a small CI/cron check that runs `SELECT tablename, policyname, qual FROM pg_policies` and fails if any financial table has `qual = 'true'` or if `safes`/`company_kpis`/`email_integrations` lack `relrowsecurity`. This directly closes the recurring "Critical RLS" finding.
2. **Extract one canonical portfolio-metrics module and make it NaN/status-aware.** Dashboard and analytics duplicate the per-company metric loop with subtly different behavior (O(n²) vs `groupBy`, `N/A` vs `0%` IRR, DPI=0). A single `buildPortfolioMetrics()` in `lib/` that handles `written-off`/`exited` status, negative cash flows, null `post_money`, and returns "—" sentinels for non-finite values would fix M-001–M-004, M-020, M-021 at once — and is unit-testable (extend `__tests__/calculations.test.ts`).
3. **Add a server-action authorization helper.** A `requireRole()` for server actions (mirroring `requireAdminAuth`) turns RLS into defense-in-depth rather than the sole gate for every financial write (M-010), and gives a consistent place to enforce viewer/associate/admin.
4. **Centralize financial input validation at the write boundary.** Route every financial insert/update through shared `lib/validation.ts` guards for amounts, percentages (aggregate ≤100%), dates, and reserve relationships (M-008, M-011–M-013, M-017). One place, consistently applied, stops bad data before it corrupts MOIC/IRR/waterfall math downstream.
5. **Make dark mode a lint-enforced invariant on data surfaces.** The cap-table (`OwnershipTable`), charts, and several report/list surfaces have light-only classes (M-016, M-029). Configure ESLint (M-033) with a Tailwind rule (or a small custom check) that flags visible `bg-white`/`text-neutral-800`/`text-slate-*` without a `dark:` counterpart, so new UI can't regress the premium dark theme.
